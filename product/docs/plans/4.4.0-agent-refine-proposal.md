# 4.4.0 Agent refine案（未採用・非アクティブ）

更新：2026-09-21。Ownerは4.3.2で見送ったAgent refineも今回検討するとした。**このファイルは提案であり、root AGENTS、CI、PCのモデル/skill設定を変更しない。**

## 1. 目的と根拠

root指示を追加し続けるのではなく、常時必要な判断基準だけにする。現在地は短いhandoff、Ownerの未実装案はアイデア帳、作業範囲はrelease plan、実装方法は対象codeへ分離する。狙いは読み直しと過剰な確認反復を減らすことで、モデル世代名を置換することではない。節約量・作業速度の改善率は未測定。

**確認**：現行rootには既に、Owner境界、通常branch作業の裁量、不要な全件テストを避ける方針がある。今回の案はそれを捨てず、長い事故説明と重複を減らす。[repo-agents]

公式案内ではglobalとprojectのAGENTS/overrideが階層的に読まれる。repoを直してもPCのglobal overrideが同じ督促を残す可能性があるため、実際の読み込み元を確認する必要がある。[official-agents]

Skillsは狭いdescriptionで用途を示し、implicit invocationを選択できる。レビューskillとpixel skillを実装の全タスクへ一律適用する必要はない。[official-skills]

Ownerが以前示したAstra固有blogは今回本文を再取得できていないため、その記事に書かれていると推測して方針を追加しない。本案は現行repoと上記公式の一般仕様、Ownerの運用希望から作った案。

## 2. 何をどこに置くか

| 場所 | 役割 | 置かないもの |
|---|---|---|
| root AGENTS | 権限・裁量・データ保護・確認の終わり方・参照入口 | 全PR履歴、巨大な必読一覧、モデル別の督促 |
| current-status | いまの実装状態、branch/HEAD、次の一作業 | 未実装案の詳細 |
| 会話記録 | どう決まり、どこを訂正したか | 新規のruntime契約 |
| アイデア帳 | 未実装Owner要望と未決値 | 実装済み・全機能のblockerという断定 |
| release plan/blueprint | 当該releaseの順序・接続先・採用案 | 恒久的なglobal命令 |
| task skill | 独立レビュー、pixel制作等の局所手順 | 本番操作の自動許可、全タスクへのFull義務 |
| tool/PC設定 | model/reasoning/並列数など | gameplayやreleaseの正本 |

当面、同じ文章をrootとskillとhandoffの三か所へ複製しない。深いdirectoryへ小AGENTSを大量に増やすのも目的ではない。

## 3. root置換の候補本文

以下はOwnerが精査して採用する場合の候補。現在のAGENTSに追加して二重適用するための文章ではない。

```markdown
# AGENTS.md

このrepoは個人運営のゲーム。必要な変更を、プレイヤーの状態を守って完成させる。Ownerへの説明は日本語。互換性・テスト件数・汎用性自体を成果にしない。

## 着手と裁量
- 最新のOwner依頼を目的・範囲・完了条件にする。調査/提案/レビューを実装や本番操作の許可へ広げない。
- 対象repo/branch/HEADと既存差分を確認する。他人の変更やstashを勝手に破棄・取込みしない。
- 目的が明確で戻せる局所判断は自分で進める。未決のgameplay・資産・公開範囲は決めず、該当部分だけ選択肢を示す。無関係な作業まで止めない。
- 再開時はproduct/docs/handoffs/current-status.mdを入口にする。既知の経緯や全履歴を毎段階で再読しない。

## 権限
- 許可されたrepoの作業branch、局所実装、隔離確認、commit/push、PR作成/更新、review投稿は依頼範囲内で進める。
- main直接変更、PR merge、deploy、本番DB/復元/配布/削除/cron変更は対象を含むOwner許可が必要。過去PRの許可を別PRへ流用しない。
- handoffはOwner/Web版ChatGPT管理。通常のCodex実装ではread-only。更新を明示依頼された時だけ変更する。
- secretをsource/log/報告へ出さない。第三者referenceはread-onlyで扱い、利用条件なしに製品へコピーしない。

## 実装とデータ
- 既存の正本設定・service・決算経路を再利用する。小さなvariantのために第二catalogや並行engineを作らない。
- 受付、実行、保存、読取をつなげて確認する。現在値の偶然の固定と必要な構造制約を区別する。
- 認可・所有・一意性・決算原子性・必要な再送防止を守る。既存資産/進行を設定変更だけで失効させない。
- 適用済みmigrationは追加差分で更新。未適用分の整理やbaselineは許可された起点を明示する。repo/schemaを本番適用の証拠にしない。
- 使用済みRuleset snapshotは上書きしない。必要な新Rulesetは原則一release一世代へ集約。SQL migrationと各種identityを混同しない。
- Turn retryは現在承認済みの運用契約に従う。変更依頼では対象失敗・同run/target/ruleset/seed・再初期化・終了条件を明示し、運用説明も合わせる。
- Ownerが退役させた旧互換や未依頼の将来機能を復活させない。必要な昔の状態はGitで参照する。

## 確認と終了
- 具体的な故障と影響から最小の確認を選ぶ。資産/所有/進行、二重決算、漏えい、通常操作/Turn停止を優先する。
- 既存代表で足りればtestを増やさない。不足だけ拡張/置換し、同じ故障のmatrixや複数層の重複を作らない。
- focusedと変更層のstaticから確認。同じ全件集合のlocal Fullはexact-head CIへ重ねない。composer test等の実行範囲は先に確認する。
- 現行通常操作の不具合、将来設定時の注意、サポート外を分ける。重大度と今回のrelease停止判断を混同せず、P2一件だけで自動HOLDしない。
- 必要な確認が通り具体的な未解消問題がなければ終了。新しい差分・失敗・根拠なしに再レビューやFullを反復しない。
- 読んだSHA/範囲、実行結果、未実施、推測、別担当報告を分ける。CI成功を別HEAD/本番の証拠にしない。

## 参照と分担
- 未決仕様はdocs/open-questions.mdの今回該当する項目だけ確認。設計や未実装アイデアを現在の実装と混同しない。
- Rulesetはproduct/docs/architecture/ruleset-authoring.md、実行コマンドはproduct/composer.json・package.jsonと対象testing資料、本番はdocs/operationsを必要時に読む。
- 分担は独立した範囲に限定し主担当が統合する。全員へ同じ全体探索/Fullをさせない。本番操作をsubagentへ委譲しない。
- model/reasoning/並列数は環境設定で扱う。会話・未実装案・実装状態は別文書へ。終了時は変更・確認・未決・commit/PRを報告する。
```

旧候補の「cron自動retryを永久禁止」という固定文は使わず、承認された現行policyとその変更手順を参照する文にした。安全性を外すのではなく、4.4.0の正式な耐性改善を旧テンプレートで妨げないための提案。

## 4. Skillsの使い分け案

`hakoniwa-independent-review`は、OwnerがhakoniwaのPR/固定SHAの独立レビュー・修正後再レビュー・横断レビューを依頼した時に適用。通常の実装、雑談、単独のP2妥当性相談に常時全手順を課さない。descriptionを狭くしたimplicit ONは候補として維持する。

pixel skillは実際にドット絵を作る時だけ。基本32×32、指定時に任意footprint、16px段ずれ、32×32分割、必要ならGIFという既存意図を維持。建物/怪獣のreferenceは必要な時だけ読む。

MCPはデータへの接続手段でありskillではない。Chatでnative skillが使えない環境なら同じSKILL.mdを手順書として参照するが、native invocationやscript実行をしたと偽らない。今回PCの実際のinstalled skill/overrideは未確認。

## 5. CIの整理は別の小変更として検討

**確認**：現行Qualityはpull_requestで起動し、文書jobとは別にPHPUnitの16shard計画もある。AGENTSを短くするだけでこの自動起動が減るわけではない。[quality]

**提案**：workflowの入口で差分を分類し、純粋な文書だけなら文書確認、PHP/SQL/依存/runner/workflowを含めば対応する本体確認、frontendならfrontendを選ぶ。未知のpathは安易にdocs-onlyに分類しない。docs内でもvalidator/script等の実行ファイルは文章と区別する。

required checkを消すだけのpaths-ignoreや、未実行をPASSと偽る集約にはしない。採用時に実際のrequired check設定を読み、分類で省略したjobと本当に実行したjobを結果上で区別する。最終releaseで必要な全体確認を残す。今回workflow変更・CI再実行はしない。

## 6. 採用時の最小作業

global/projectのAGENTS.override、ネストしたAGENTS、skill本文を一度確認し、権限境界・停止条件の矛盾だけを整理する。モデル世代が変わったという理由で全設定を作り直さない。

Ownerがroot候補を採用したら通常branchで置換し、次の実作業で「入口だけで開始できる」「具体的な不足のないFull反復をしない」「未実装案を仕様化しない」を確認する。プロンプト専用の巨大CIや新しい恒久テスト群は作らない。改善が測れないうちにトークン節約率を断定しない。
