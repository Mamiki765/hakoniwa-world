## 変更範囲

- v27の有効payloadを15個の `config/hakoniwa/rulesets/current/` domainへ展開し、
  v16〜v26のsourceと世代別overrideを撤去する。v27 entrypointは現行domainだけを合成する。
- authoring validator／inspector、現行turn skill snapshot、初期島配置、publisherを
  基準schema／現行contractへ絞る。旧世代のupgradeクラス11件を撤去する。
- 旧migration44ファイルを、最終schema dumpと
  `2026_10_02_000000_install_4_9_0_baseline` 1ファイルへ一本化する。
  test templateの指紋にも新しいschema／baseline manifests／seed authorityを含める。
- 旧upgrade専用testを撤去し、現行でも残り得るskill rebuild状態と保存catalog identityの
  保証へ置換する。validator summaryの単なる入力コピーと固定catalog個数の期待も整理する。
- PR184の固定SHA `495d319e9e0f296538fc9f3ece1b8642393b5872` から、
  `CompleteTurnEngine` のphase内query集約を採用する。PR184自体はmergeしない。

v27の値・型・list／map形・キー順は変更しない。元payloadと厳密比較したchecksum:

`f353eb5a409657809a1e3ebdcc5fa6dcd7f700ba6b0a6bc5165313cd32c1d3f4`

分類は15 domains／3138 scalar leaves（Behavior 2040、Data 836、Flavor 262）。
これはsource変換の同値検査であり、本番DBの適用状況の証拠ではない。

## Fresh install

PostgreSQL 18.4上で基準SHAの旧schema dump＋migration chainから最終構造を取得した。
schema-only dumpにはユーザーデータ、旧migration台帳、過去catalog rowsを含めない。
既存Laravel schema loaderが最終schemaをロードし、1 migrationが現行global catalog、
published v27とcommand／production／monster definitions、商人会話seed 2件を作る。
WorldとUserはmigrationでは作らない。World初期化は既存operator手順による。

空の新規DBに通常の `php artisan migrate --force` を実行する。
Laravelのschema dump用PostgreSQL clientも必要である。fresh完了後の台帳は新markerのみ、
published Rulesetはv27のみとなる。freshの採番値は既存環境の値と同じである必要はない。
IDを定数として扱わずFKで参照する。再実行はpending migrationなしとなる。

## 既存DBの採用

既存環境への本番適用はOwnerの別承認が必要。このPRでは実行しない。

1. 通常runbookに従いbackup／復元手順と実際の台帳・schemaを確認する。
2. **コードを入れ替える前に**、旧環境が承認基準4.9.0まで完了していることを確認する。
   それ以前の環境は、このPRのコードで旧upgradeを実行できない。
   固定基準SHA側の既存手順で先に4.9.0へ到達させる必要がある。
3. 新コードで `php artisan hakoniwa:baseline:check` を実行する。
   このcommandは読み取りのみ。publicのtable／column型・nullability・default・constraint・
   index・trigger・function・sequence設定の指紋、必要な旧台帳名、現行global catalog、
   immutable v27 payload／definitionsと共有Worldの参照を確認する。
4. 検査が成功したDBだけで、Owner承認後に通常の `php artisan migrate --force` を行う。
   既存採用pathはbusiness dataを読むだけで、Laravelが新markerを1行追加する。
   旧台帳の行、Ruleset ID、FK、sequenceの現在値、World／queue／TurnRun、資産・進行は保持する。
5. 再度check／migration statusと既存operator確認を行う。migrationのdownはforward-onlyで拒否する。

台帳が欠ける、共有Worldが旧Rulesetを参照する、catalog／snapshotが異なる、schemaが未知の場合は
**停止する**。台帳を偽造・削除して合わせる、IDを振り直す、queueを再束縛する、
reset／fresh／drop／CASCADEで合わせる処理はない。追加変換が必要なら、実データの差分とriskを
Ownerに提示して別判断を受ける。

`hakoniwa_diagnostic` のview／function／権限はMCP側の運用authorityであり、このmigrationは
作成・drop・grant・修復しない。既存採用pathにpublic DDLがないため、その依存先を保つ。
freshで診断機能が必要なら、MCP側の現行手順を別途適用する。

## 構造指紋の限界

PostgreSQLがpg_dumpのCHECK式を再解析すると、同値なtyped arrayのSQL表記が変わる。
PR185当初は旧chain完了fixtureと新dumpロードfixtureをそれぞれ178 objectの指紋として保持した。
その後の本番read-only検査でmigration ancestryとの差を検出してdeployを停止した。
現行の修正範囲、176 objectの完全な受入集合とMCP側の契約は
[4.9.2構造修正](4.9.2-baseline-structure-fix.md)を参照する。
弱い文字列正規化や条件の部分一致は使わず、確認した全体構造との一致を要求する。

PR185当初の検証対象はPG18.4の隔離DBで、本番の実際のledger／SQL表記は未確認だった。
合法なSQL表記差でもcheckが止まる可能性があり、その場合はOwnerが差をレビューする。
指紋はACL、owner、他schema、sequence現在値、診断schemaを基準化しない。それらを変更もしない。
本番のintegrity／permissionsと診断動作の確認は通常operator手順で別途必要となる。

## 棚卸し資料とOwner判断

指定の棚卸しは基準 `5b12de95`、158 files／1211 tests＋helper1。
Library index `libfile_437582bc13f88191930d1f60efa9f6de`、DB保証
`libfile_b4bc9c640a948191a19f902795f5c64b`、MD／JSON ZIP
`libfile_57484bf7eba8819188cca85ed9c07d62`、CI分割計画
`libfile_2b46808585e8819181c30fd5cb72ad2c` を指定されている。
公式materialize helperはWindows `os.setxattr` 未対応で一度失敗した。
同一PCの既存Python Linux runtimeで、同じ未変更のhelperと完全なprepare_materialize transferを
使って4資料を取得した。専用volume `hakoniwa-v27-library-20261002` の `/artifacts/` で
存在・読取・SHA256・`user.library-file-id`／version metadataを確認した。raw curl等は使っていない。
索引の158 files／1211宣言と、CIの1121実行識別子は、言語・provider展開・基準SHAが異なる集計である。
原資料の取得proofと変更対象caseの抽出を最終ZIPへ含める。

CI計画は既存LPTへ成功full runのJUnitを渡す配線案であり、file秒数が未保存のため短縮率は未確定。
今回は16 shardとserial／sharded identifier同値検査を維持し、履歴artifact配線の変更は採用しない。
テスト整理の効果とCI配線の効果を混同せず、専用比較full CIや任意dispatchは実行しない。

Owner判断が必要な点は、実DBのpreflight結果と停止時の追加変換、旧基準未達環境の扱い、
診断schemaのMCP側手順、最終review／CIを見たうえでのmerge／本番適用である。
最終artifact保存と確認したLibrary IDを親へ報告する。
