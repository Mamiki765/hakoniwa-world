# 始末書：バハムルの仕様確認を欠いた数値調整

2026-09-23。実装担当Agentの作業について記録する。

## 起こしたこと

私は、バハムルの技と対処方法を揃えずに数値調整を進めた。Ownerに何度も仕様漏れと不自然な調整を指摘させ、不要な測定と修正を重ねた。時間・usageとOwnerの確認負担を増やした責任は実装側にある。

1. 初級4技・中級5技の構成から黒爪と竜翼を落とした。単体強打という役割がない状態で、通常攻撃の素の能力を上げて埋めようとした。
2. その結果、初級1の武力が初級2・3より高い逆順の数値を作った。技倍率が共通であるだけでは、この不自然な設計を正当化できない。
3. 「低Lvでは勝てない」の判定に時間切れを含め、苛烈な攻撃で敗北するという戦闘体験の確認を後回しにした。生命へ極振りしたタンクだけが残るケースを、勝率0だけで十分と扱ってはいけなかった。
4. 攻撃能力の調整を戻す際、HPまで旧値へ下げた。Ownerが指している範囲を確認せずに変更を広げた。HPはその後42,000 / 100,000 / 140,000へ戻した。
5. 技の欠落が判明した後も、竜翼の攻撃低下を落としたまま追加・測定し、再度指摘を受けた。仕様を一覧にして照合する前に実装へ戻ったことが原因である。
6. 咆哮の覚醒ゲージ補充はsourceに存在したが、汎用の代用敵によるtestを、実バハムル全体を確認できたかのように扱える状態にしていた。実際には技構成の漏れを検出できていなかった。
7. 最後に追加した実catalogの代表testも、不正なsnapshot fixtureで2件ともエラーになった。0 assertionsであり、確認を前進させた結果として報告できない。

## 原因

最初に「Ownerの確定条件」「過去の提案」「現在のcode」「まだ確かめていないこと」を一つの照合表にしなかった。会話と文書の一部から判断し、指摘された箇所だけ直して次の測定へ進んだ。

戦闘設計を、HP・攻撃力と勝率の調整へ縮めた。黒爪を誰が受けるか、全体攻撃からどう回復するか、竜翼の弱体で何が変わるか、予告に対応する機会があるか、という役割を先に実証しなかった。必要な技がないことによる症状を、別の能力値で直そうとした。

さらに、完全な戦闘条件を固定する前に、複数のAIや能力値で試行を増やした。mechanics変更で前の結果が無効になった時点の整理も遅れた。計算量やtest件数は、この確認順序の誤りを補わない。

## 影響

- 完全な技構成での4段階の難易度は、停止時点で未完成。
- 黒爪・竜翼がない状態で得た中級の研磨差などは、完成版の根拠として撤回する。
- 追加の実装、測定、文書修正、Ownerによる再指摘にusageと時間を使った。
- HはWIPと攻撃能力の撤回commitまでpush済み。新しい技・弱体・未成功testはlocalの未commit変更。HのPR、merge、production deploy・DB変更は行っていない。

## 調べ直した設計の基礎

[Ian SchreiberのGame Balance Concepts](https://gamebalanceconcepts.wordpress.com/2010/07/07/level-1-intro-to-game-balance/)は、観測された不均衡が原因とは限らず、修正前に原因を掘り下げる必要を説明している。今回の適用先は、欠落した単体強打を通常攻撃力で代用しないこと、勝率0の内訳を調べることである。

[Soren Johnsonの難易度設計論](https://www.gamedeveloper.com/game-platforms/analysis-designing-games-to-challenge-diverse-players)は、固定された相手に対して成長を実感できることと、挑戦と余分な罰を区別することを論じている。今回の固定ボスでは、Lvや装備を上げた効果と、AIで対処した効果を分けて確認する。Ownerが求めていない自動難易度補正や、特定buildだけを潰す新機構を導入する根拠にはしない。

これらを読んだこと自体は修正完了の証拠ではない。今回の仕様はOwnerの指示を正本とし、実装と戦闘の挙動で確認する必要がある。

## 停止時に整理したことと、まだ出来ていないこと

- 現HEAD、未commit変更、撤回する測定、失敗したtestを[チェックポイント](../plans/4.4.0-bahamul-checkpoint.md)へ残した。
- 逆順の攻撃能力と、指示範囲を超えたHP巻戻しは撤回した。
- 黒爪・竜翼・既存攻撃低下の追加は途中。sourceにあることと、実戦で確認したことを区別して記録した。
- 咆哮のゲージ補充について、既存helperが覚醒済み等を対象外にすることも記録した。「全仕様に抜けがない」とは結論していない。
- 実catalogのtest修正、4段階の再調整、UI残件、最終検証は未完了。再発防止策が実行・検証まで完了したとは主張しない。

## 再開時に守る作業順序

1. **仕様照合を先に終える。** 技の名前だけでなく、対象・効果・弱体・予告・覚醒・段階差をOwner発言とcodeへ対応させる。提案をOwner決定へ読み替えない。
2. **実際の定義で挙動を確認する。** 代用敵のtestだけでは足りなかった接続を代表戦闘で確認する。balance値そのものを大量の固定値assertionで縛らない。
3. **比較条件を固定する。** 能力配分、装備、研磨、AI、seedを記録し、途中で変えたら別実験として扱う。平均・分散・極振りの結果を混ぜない。
4. **結果の内訳で判断する。** 勝利・全滅・時間切れ、倒れた役割、予告後の対処、戦闘時間を見る。目標勝率に近いだけで完成としない。
5. **変更が根拠を失わせたら止めて整理する。** 技や弱体を追加した後は、追加前の数値を完成根拠へ流用しない。再確認の必要性が説明できない追加計測を重ねない。
6. **結果を誇張しない。** focused PASS、実戦測定、CI、未確認を分ける。失敗したfixtureを修正済みとして扱わない。

この順序をAGENTS.mdへ事故ごとの文言として追記することはしない。既存原則を守れなかった問題として記録し、現在の差分と検証で対処する。

Ownerの停止指示に従い、本書の保存後は実装・測定・test・pushを続行しない。
