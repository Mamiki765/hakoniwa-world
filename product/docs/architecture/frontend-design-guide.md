2026-10-10〜11-03 に画面（`product/resources/`）の再設計と、その後の画面側の作業を担当したラピス（Claude）が、次に画面を触るAgentへ残す設計ガイド。

- 優先順位は **Ownerの明示指示 ＞ `AGENTS.md` ＞ この文書**。この文書は「なぜ今の見た目なのか」「どこに何を書くか」「何をすると壊れるか」の記録で、Ownerの新しい判断があればそちらに従い、この文書を置き換える。
- 書いてある決まりの多くはOwnerが実物を見て決めたもの。「Owner決定」と書いた項目は、見た目の好みで戻さない。変えたいときは止めてOwnerに聞く。
- 細部（数値・class名）は変わる。迷ったら現在のCSS・Vueを正本にし、ここは考え方として読む。

## 2. 基本の考え方

### 2.1 地上と地底で感覚を分ける（Owner決定）

- **地上（箱庭）＝シム系**。帳簿のように全部を同時に見せ、密度を高く。細い罫線、角丸は小さく（New は3px、Old は0）、影は浮かせる物（ダイアログ・ポップアップ）だけ。地図は常に海の色の上に置き、タイルより目立つ装飾を置かない。
- **地底（FFA）＝RPG／ソシャゲ系**。立ち絵と背景が主役で、情報は縁に重ねる。拠点は「上に所持金、下にメニュー」の枠。イベントシーンと戦闘は枠を消して全面。
- 秘書はその中間。地上側の色で、メインはステータスシート風。

### 2.2 情報の出し方

- **「それ、要ります？」から始める**。画面に足す前に、プレイヤーがその画面で次に何をするかを考え、要らない物は出さない。迷ったら出さずにOwnerへ聞く方が、後から削るより安い。
- 1画面に主役は1つ（開発画面＝地図と計画、TOP＝島一覧、地底ホーム＝立ち絵）。
- 同じ説明を毎行に書かない。記号と凡例1か所で済ませる（ターン消費の■□）。
- 幅で項目を出し分ける。地上のHUDは `lv2`（スマホで隠す）・`lv3`（広い画面だけ）。隠した項目は別の場所（観光のマス情報欄など）で必ず見られるようにする。
- 色だけで状態を伝えない。警告・エラー・選択は別の色相にし、文字か形も添える。
- 英語の飾りは使わない。固有の表記（KARMA など、Ownerが英語のままと決めた物）は例外。
- 内部用語（hash、rule、cooldown、ID）をプレイヤー画面に出さない。

### 2.3 操作の決まり

- **禁止より知らせる**。資金・輝石が足りないコマンドも予約できる（「資金が○不足」を添えるだけ）。止めるのは計画が一杯の時だけ。
- 確認ダイアログは**溢れる・消える時だけ**出す（計画一括は押し出しで消える計画がある時だけ）。日常の操作に毎回確認を挟まない。
- 取り返しのつかない管理操作は必ず2段（確かめる→実行）。確かめる画面に対象・量・戻せないことを出す。
- 判定をフロントへ写さない。使える・使えない、候補数などはserverの値を使う。画面側で同じ判定を作ると二重になり、いずれずれる（`AGENTS.md` §6）。
- 補助の表示（ブーストの帯、通知など）はAPIが失敗したら**何も出さない**。エラー文で本文を押し下げない。
- 遅れて返ってきた古い応答で表示を戻さない（島を続けて開いた時など。既存の世代チェックを使う）。
- ページが裏にある間は「既読」にしない。

### 2.4 目立たせすぎない

新機能は既存の画面に**同じ文字の大きさ・色で添える**のが基本。Ownerは「一覧が汚れた、主張しなくていい」を何度か言っている。

- 船・首都の名前: 一覧にボタンを置かず、名前を前に添えるだけ。付け替えは地図で選んだ時のマス情報の下の小さなボタンだけ。
- ブーストの予告・開催中の帯: TOPだけ。島・地底では出さない。
- 赤丸の通知は、本人が次に見に行くべき物だけ（伝言板の新着、露店など）。

## 3. 色とテーマ

### 3.1 仕組み

テーマは8種類: `system`、`light`（New Light）、`dark`（New Dark）、`old-light`、`old-dark`、`skyblue`、`autumn`、`black`。

- 保存は既存の cookie `hakoniwa_theme` と `<html data-theme>`。別の仕組みを作らない。
- `system` は端末の明暗で New Light／New Dark を選ぶ。保存済みの `light`／`dark` は New として扱う（Owner決定）。
- 許可値は3か所で同じ並び: `product/resources/js/App.vue` の `themeModes`、`product/resources/views/app.blade.php`・`manual.blade.php`・`community-guidelines.blade.php` の `in_array`。

トークンは2層ある。

| 層 | 名前 | 置き場 | 使う画面 |
|---|---|---|---|
| 基本 | `--ink` `--muted` `--paper` `--paper-deep` `--canvas` `--line` `--navy*` `--coral*` `--gold` `--danger*` `--warning*` `--success*` `--info` `--input-*` `--hover-surface` `--selected-surface` `--table-heading` `--on-solid` `--toast-*` `--shadow` など | New＝`new-theme.css`、Old＝`hakoniwa.css` 冒頭、SkyBlue・Autumn＝`legacy-themes.css`、Black＝`black-theme.css` | 秘書・地底・交易場・周辺画面・マニュアル |
| 帳簿 | `--sl-*`（`--sl-bg` `--sl-panel` `--sl-ink` `--sl-accent` `--sl-turn` `--sl-good` `--sl-bad` `--sl-sea` `--sl-map-*` `--sl-radius` `--sl-f-*` など） | `surface-ledger.css` 冒頭に、テーマごとに1組ずつ | 地上の開発画面・観光（`.sl`）、TOP（`.tp`） |

地底は `.ug-shell` で `--ug-surface` `--ug-raised` `--ug-accent` を基本層から作っている（`underground.css`）。地底だけ別の切り替えは作らない。

### 3.2 守ること

- **画面側の規則に色を直接書かない**。必要な色が無ければトークンを1つ足し、**全テーマに値を入れる**（足し忘れると、そのテーマだけ既定値や透明になる）。
- Old Light／Old Dark は「旧CSSを新しいDOMに当てる」のではなく、旧画面の色と書体（Georgia系の見出し）を**トークンの値として写す**。旧CSSは旧DOMのselectorに依存しているので、新しいDOMには当たらない。
- SkyBlue・Autumn の見出し飾り（背景画像つきh2）は帳簿の細い見出しには当てない。
- 警告（橙〜黄）・エラー（赤）・選択（青）は別の色相。New の値は `new-theme.css` 冒頭のコメントのとおり。
- disabled は `opacity` で一律に薄くしない。variant と muted の組にして、押せなくても読めるようにする（Black の文書 `black-theme.md` と同じ）。
- ゲージの上の数字は、色付き・空のどちらの上でも読めるよう白字に濃い縁。
- ダークで「灰色の地に白文字」の行は押せないボタンに見える。一覧の行はパネル色の上に置く。
- 既存の直書きの色（地底のボスの残り時間の赤、覚醒ゲージの枠など少数）は負債。触る時にトークンへ寄せる。新しく増やさない。

### 3.3 テーマを足す・直すとき

1. 基本層の値の組を1つ（専用のCSSか既存のテーマCSSに）。
2. `surface-ledger.css` に `--sl-*` の組を1つ。
3. `themeModes` と blade 3か所の許可値、オプション画面の選択肢。
4. 全画面をライト系・ダーク系それぞれで撮って確かめる（§5.3）。

## 4. 書体と数字

- New の本文: `--sl-f-body`（BIZ UDPGothic → Noto Sans CJK JP → ヒラギノ角ゴ → Yu Gothic UI）。見出しも同じゴシックで太さだけ変える。
- Old の見出し: Georgia, "Yu Mincho", serif（旧画面の再現）。
- 数字は `font-variant-numeric: tabular-nums` で桁を揃える。地上は `.num` / `.sl-num` / `--sl-f-num`。
- 地底の数字（所持金・能力値・HP・IL・品質など）は `--ug-f-num`（Georgia系セリフ）。差し替える時はこの変数だけを変える。かな・漢字の地の文は変えない。
- **Webフォントを外部から読まない**（Google Fonts など）。新しい外部サービスの利用にあたるので、Ownerの判断が要る。ドット風の書体も未決のまま。

## 5. スマホ幅

### 5.1 確かめる幅

**320 / 360 / 1280px、ライトとダーク**。必要なら 390（iPhone）と 768（タブレット）。320で崩れなければほぼどこでも崩れない。

### 5.2 崩さないための決まり

- ページ全体を横にはみ出させない。gridの列は `1fr` ではなく `minmax(0, 1fr)`（長い単語や入力欄があると `1fr` は縮まない）。
- 横に長い表はスマホ幅（640px以下を目安）で**1件ずつのカード**にする（交易場の出品一覧）。表を横スクロールさせて価格・ボタンを画面外に置かない。
- 日本語の短い語が1文字ずつ縦に折れないようにする（スキル名、ボタン名）。狭い時は横に並べず下の段へ回す。ボタンの文字は `white-space: nowrap`。
- 指で押す物は高さを確保する。目安はツールバー・小ボタン30〜36px、ダイアログの決定ボタン44px。
- ダイアログはスマホで下からのシート（`.sl-dialog`）。下端は `env(safe-area-inset-bottom)` を足す。
- マウスを載せた時だけの詳細（地図のマスのふきだし）は、指の操作では出さない。同じ内容を下の欄に出す。
- 区切りの目安（今の実装）: 760px（地上・地底のスマホ組み替え）、1180px（`lv3` を隠す）、860px（TOP）、640px（表→カード）、480/360/340px（狭い端末だけの微調整）。地底は `container: underground` のcontainer queryで、枠の幅を見る。
- 地上の開発画面のスマホは、地図が上（高さ42%）、その下にタブ。タブ右端の「︽」で地図とHUDを隠して入力に専念できる（Owner決定）。
- 地底の拠点は画面の高さに収め、本文だけをスクロールさせる。下のメニューは6つ。狭い幅では文字を詰めて枠に収める。

### 5.3 撮って確かめる

見た目の変更は**撮った画像を見てから**PRに出す。見ていない画面を「確認済み」と書かない。

- 一番確かなのは、作業機で本物のサーバーを立てて撮る方法（PHP 8.5 と Postgres をコンテナで起動、スキーマ→migrate→`hakoniwa:world:init`、git管理外のログイン用ファイルでログイン）。地底APIは60回/分の制限があるので撮影の間を空ける。
- API未接続の画面を先に作る時は、モック付きのプレビュー（`product/tools/` 配下に置き、`.git/info/exclude` で除外）でよい。commitしない。
- PRには変更前後の 320/360/1280・ライト/ダークの画像を付ける（全部でなくても、変えた画面の代表を）。

## 6. 画面ごとの決まり（Owner決定を含む）

### 6.1 地上の開発画面（`.sl`、`surface-ledger.css`）

- 3列（マス・コマンド｜地図＋ログ｜計画）。左右の列幅は境目のドラッグで変えられ、端末に保存する。全体ナビの下の高さにぴったり収め、ページ全体はスクロールさせない。
- コマンドは既定で「いまのマスで使える物だけ」。「全部出す」で、いまの地形では使えない物も「先読み」の印つきで入れられる（埋め立て→埋め立て→地ならしの仕込み）。「使える」は地形などの対象条件で決め、資金・輝石の不足では隠さない。
- 計画の行を選んでいるとその**前**へ、空き枠を選んでいるとその枠へ、選んでいなければ末尾へ入る。入れる位置をコマンド欄の上に小さく出す（スマホで計画が見えない時用）。
- 一括の先頭は「荒地と焦土を全て地ならし」。一括は選択なしなら1番から、選択ありならその位置から入れ、元の計画は下へ送る。上限を超えた分は押し出して消える（昔の箱庭と同じ、Owner決定）。何件入り何が溢れるかはserverに確かめ、溢れる時だけ選択肢を出す。
- 一言コメントは島名の右。押すとその場で書き換え。スマホは本文を出さず小さなボタンだけ。
- 地図: 天候は左下に大きく。選択マスは黄の枠。計画番号は右上の小さな札。

### 6.2 観光（他の島を見る）

開発画面と同じ組み方で、計画の列が無い2列。持ち主にしか見えない情報は落とす。上の1行で幅のため隠した項目は、マス情報欄に全部出す。

### 6.3 TOPと島一覧（`.tp`、`top-ledger.css`）

- PCの島一覧は2段組み。上段に島名・賞・数値、下段に「島主＋秘書：一言コメント」を数値の列まで割り込ませる。順位は2段にまたがる。
- 賞は「賞×3」とまとめず1つずつ。同じ列に討伐・KARMA（英語のまま）・資金繰り。画像は既存の prize 画像を AssetManifest で解決する。
- スマホは行カード。並べ替えに選んだ項目を右に大きく出す。お知らせと問い合わせは島一覧の上。
- ブーストの帯はTOPだけ。

### 6.4 秘書

メイン（アイコンタブ、左に立ち絵、右にステータス・祝福、下に経歴と地上・地底の装備2列）は**崩さない**。熟練度は EXP / NEXT と経験値バー。狭い幅では経験値を名前の下へ。

### 6.5 地底（`underground.css`、`Underground*.vue`）

- 拠点の枠: 上に所持金、下にメニューを固定。イベントシーン・戦闘は枠なし。
- ホームは立ち絵が主役。案内人と行商人はホームに出さない。左上に秘書の状態と「今やれること」（STPの残り、歪んだ輝石の受取など）、下にパーティーと出発。
- ショップは案内人（名前はプレイヤーが付けた物）、交流場は行商人アキ・インキュバスの店として、背景と立ち絵を敷いて中身を重ねる。
- STP配分の＋−は押しっぱなしで加速、数字の直接入力も可。決めるまでやり直せる。
- 場面素材は `resources/scene-assets/scene-assets.json` のmanifestで解決する。**画像を加工・再配布しない。提供された非AI作品を画像生成の入力・参照に使わない**（`scene-assets/README.md`）。AI非表示の設定では、AI生成の背景は水晶へ、立ち絵・スチルは出さない。

### 6.6 戦闘ログ・再生

- 1対1と多人数は同じ部品。人数でカードの大きさだけ変える。
- 「要点」は会心・覚醒・予告・撃破だけ、ラウンド見出しに与えた／受けた／回復の合計。「すべて」で全行動。読んでいるラウンドの見出しを上に残す。
- 再生は1行動ずつ、小さな数字が続けて出てラウンドが終わると合計が大きく残る。連続再生中はラウンド合計で止めず次へ。
- MP: 自然回復以外の増減を青系の ±MP で出す。

### 6.7 交易場・周辺画面

周辺画面（交易場・お知らせ・オプション・アカウント・お問い合わせ・管理）は `panel-pages.css` で開発画面・TOPと同じ密度にそろえる。お知らせ本文（Markdown）の見出しには当てない。交易場はスマホでカード。ページ送りは2ページ以上ある時だけ出す。

### 6.8 管理ページ

左に項目・右に作業。取り返しのつかない操作は2段。手動ターンのボタンは時間制限があるので、運用はCLIが正（画面で長い処理を走らせない）。

### 6.9 マニュアル（`product/docs/manual/`）

- 範囲は「遊び方と各機能の概要・施設索引・コマンド索引・詳しいことは画面へ案内」。**確率・計算式・怪獣の能力値・アイテム個別の効果・地底後半・隠し仕様は載せない**。
- 何が隠しかはOwnerが決める。決まった範囲は `product/docs/manual/README.md` 7章。新しい版で書き足す時は、書く前に載せる範囲をOwnerに聞く。
- 索引の数値はRulesetから自動表示（`indexes.php` には文章だけ）。マニュアルに数値を手で写さない。

## 7. どこに何を置くか

### 7.1 CSS（`product/resources/css/`）

読み込み順は `app.css` の `@import` の順で、後ろほど強い。

| ファイル | 中身 |
|---|---|
| `hakoniwa.css` | 旧来の全画面の規則と、Old Light／Old Dark の基本トークン。秘書・交易場・伝言板・戦闘ログなど、まだここに残っている画面がある |
| `new-theme.css` | New Light／New Dark の基本トークン（値の組だけ） |
| `underground.css` | 地底の枠（`.ug-*`）、拠点の固定枠、`--ug-f-num`、再生、地底のスマホ調整 |
| `legacy-themes.css` / `black-theme.css` | SkyBlue・Autumn・Black の基本トークンと、それぞれの最小限の上書き |
| `surface-ledger.css` | `--sl-*` のテーマ別の組（冒頭）と、地上の開発画面・観光（`.sl`） |
| `top-ledger.css` | TOPと島一覧（`.tp`）。色は `--sl-*` |
| `panel-pages.css` | 周辺画面の枠の密度 |
| `manual.css` | マニュアル（別ページ） |

- 新しい画面の規則は、その画面のファイルへ。どこにも属さない小さな物だけ `hakoniwa.css` の末尾へ、節のコメントを付けて。
- 節の頭に「何のための規則か」を日本語1〜2行で書く（今のファイルの書き方）。版番号だけの見出し（`/* 5.5.0 露店 */`）は後から読むと意味が分からないので、内容で書く。
- 狭い幅だけの修正には「何が崩れるから」を書く（例: 「320px前後では『キャラクター』が隣の『ショップ』とくっついて読めるので…」）。

### 7.2 Vue・TS（`product/resources/js/`）

- `App.vue` は全体の殻（ナビ・TOP・島画面の枠・オプションなど）でまだ大きい。**新しい画面や切り出せる塊は `components/` へ**。改修後に問い合わせ・お知らせ編集・戦闘ログ・STP配分などを切り出してきた流れを続ける。ただし状態の共有が多い物（案内人の部屋など）を無理に割らない。読みやすくするために複雑にしない。
- 画面の計算だけの小さなTSは部品の隣に（`undergroundBattleLog.ts`、`undergroundStpDraft.ts`、`undergroundEquipmentSlots.ts`）。同じ名称表を複数の部品に書かない。
- API呼び出しは `api/`、表示用の整形は `formatters/`、画面をまたぐ状態は `state/`、地図の座標計算は `map/`。
- 新しいAPIに画面を先に合わせる時は、受け口を1ファイルに閉じる（`boosts.ts` の例: 仮APIから本APIへの差し替えがそのファイルだけで済んだ）。
- 型は `types.ts`。
- testは `*.surface.test.ts` / `*.underground.test.ts` / `*.shared.test.ts`（`npm run test:surface` などのproject分け）。

### 7.3 文書

- この文書: `product/docs/architecture/frontend-design-guide.md`
- テーマの出典: `product/docs/releases/4.7.0-ui-themes.md`（SkyBlue・Autumn）、`product/docs/architecture/black-theme.md`
- マニュアルの書き方と範囲: `product/docs/manual/README.md`

## 8. 進め方

1. Ownerの言葉で「何に困っているか」を確かめる。分からなければ一番ありそうな読みで進め、どう読んだかを書く。
2. 大きな見た目の変更は、実装の前に**比べられる実物**（試作か、作業branchの画面のスクリーンショット）を出す。案が複数あるなら並べる。Ownerは設計書ではなく実物で判断する。
3. 1画面＝1PR。無関係な画面、広いrefactor、server・API・schemaの変更を混ぜない。server側が要ると分かったら止めて報告する。
4. 撮って確かめる（§5.3）。PRに前後の画像、確かめた幅とテーマ、確かめていない所を書く。
5. Ownerの感想は、次に同じ判断をしないで済むよう、この文書か該当の仕様文書に「Owner決定」として残す。

testは `AGENTS.md` §7 に従う。画面のtestは「ラベルと値の対応」「挿入位置のような壊れると困る振る舞い」だけ。文言・DOM構造・class名・表示順・色を固定するtestは足さない。見た目を直してtestが赤になったら、写経の固定一致を疑う。

## 9. やってはいけないこと

- 画面側の規則に色を直接書く。トークンを足して全テーマに値を入れずに済ませる。
- テーマ専用の別の切り替え・保存の仕組みを作る（地底だけの配色切替など）。
- 外部のWebフォント・CDN・新しいUIライブラリを、Ownerの判断なしに入れる。
- 秘書メインの組み方、帳簿の3列、TOPの2段組み、地底の上下固定の枠、スマホの「︽」など、Owner決定の配置を好みで戻す・作り替える。
- 英語の飾り見出し・キャッチフレーズを足す。内部用語をプレイヤー画面に出す。
- 新機能を目立たせるために、一覧へボタンや色付きの札を足す（§2.4）。
- serverの判定（使えるか、候補数、価格）を画面側で写して作る。資金不足を理由に予約を禁止する。
- 日常の操作に毎回確認ダイアログを挟む。取り返しのつかない操作を1クリックにする。
- 補助の表示でAPIエラーを大きく出す。遅れた古い応答で表示を戻す。
- ページ全体を横にはみ出させる。表を横スクロールさせて大事な値やボタンを画面外へ置く。
- 撮っていない画面を「確認済み」とする。
- scene-assets の画像を加工・再配布する、画像生成の入力に使う。試作の仮のドット絵・仮の名前・仮の数値を本体へ持ち込む。
- マニュアルに確率・計算式・隠し仕様・Rulesetの数値の手写しを書く。載せる範囲をOwnerに聞かずに広げる。
- 見た目の変更のPRに、server・API・schema・Rulesetの変更を混ぜる。
