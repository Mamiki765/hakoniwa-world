# 4.2.1 ログ保存・地下統計・過去データ整理計画

Status: Implemented on `release/4.2.1`; production apply、deploy、cron変更、mergeは別Owner gate。

基準は2026-09-16にForgejoで再確認した`main` `a7b0eebaa1a77a2bc90919f6dcf8b1686a9ee6fb`。4.2.0のproduction適用状態は推定しない。Surface Rulesetのsemantic changeはなく、v26を維持する。

## 1. 保存境界

| 対象 | 恒久保存 | 期限付き | 整理 |
|---|---|---|---|
| `underground_battles` | 結果、報酬、request identity、compact履歴、`statistics_version`と小さい統計 | `initial_state`、party表示member、portrait event | `compaction_version`単位でbattleごとに変換 |
| `underground_battle_logs` | なし | actionと詳細presentationを終了1時間まで | bounded cleanup |
| `underground_parties` | content、leader、人数、報酬authority | なし | 現在の小さいsnapshotを維持 |
| `underground_party_members` | identity、source、level、小さい表示情報 | 完全buildは保存しない | battleと同じtransactionで旧snapshotを縮小 |
| 画像lease | path、battle/request identity、期限 | 詳細と同じ期限 | bounded cleanup。現在画像と有効leaseの条件付き削除を維持 |
| 貸出・ticket台帳 | 現行正本を維持 | なし | snapshot縮小と分離し、件数やdeltaを再計算しない |
| routine Surface audit | `turn.summary`のNation×確定Turn集計 | なし | 対応summaryを検証できるallowlistだけを明示変換 |

新規writerは、戦闘計算用の装備、AI、完全build、全combat stateを恒久battle/memberへコピーしない。期限内表示に必要なstate、member表示、portraitはbattle log側へ置く。期限後もplayer名、遭遇名、結果、報酬、履歴用summary、request fingerprintを残し、再送で戦闘・drop・貸出報酬を再決算しない。

## 2. 統計version 1

`statistics_version = 1`と小さいJSONを1戦1行へ保存する。これはgameplay設定authorityではなく保存形式である。

- battle列と統計header: activity、party人数、runtime identity、記録source。
- `party`: 味方全体の与damage、被damage、実回復、軽減、戦闘不能、蘇生、覚醒人数。
- `self`: leader本人の与damage、最大一撃、被damage、実回復、軽減、敵撃破、通常攻撃、skill、critical hit、MP消費・回復、最低／終了HP、戦闘不能回数、蘇生された回数、蘇生した回数、戦闘中覚醒、覚醒round、覚醒技使用回数。

与damageは実HP減少とbarrier消費の合計で、overkill表示値を足さない。回復は実際にHPが増えた量だけで、overhealを含めない。軽減は防がれたtargetへ帰属する。通常攻撃／skillはactorのdecision回数で、canonical action key別の小さいusage mapも残す。criticalはcriticalになったdamage hit数、最大一撃は一回のattack/action sequenceが一対象へ与えた実damageとし、敏捷による2〜4連撃は分割せず合計する。同じAoE actionでも別対象へのdamageは合算しない。最大記録にはcanonical action keyとdamage sourceを添える。同値時はcanonical key順で決定する。戦闘不能・蘇生は状態遷移の発生回数である。覚醒は開始時状態と戦闘中発動を分離するが、覚醒発動そのものに付随するHP全快は回復統計へ含めない。生命讃歌等の覚醒技が行う回復は、通常回復と同じく実際にHPが増えた量だけを数える。強制覚醒を持つ決闘はactivityで通常集計から分離できる。

damageは`direct`・`periodic`（DOT）・`counter`、healingは`direct`・`periodic`（HOT）・`lifesteal`・`regeneration`・`revival`・`awakening`のsource別にも小さく集計する。healingの`awakening`は生命讃歌等の覚醒技による回復を指し、覚醒発動時の全快を指さない。DOT/HOTは既存log rowのactor（受給者）を変えず、追加metadataの`source_combatant_id`、source side、受給者identity、status keyを統計projectorが読む。PTだけはactor identityを必須とし、soloは味方が本人だけという確定条件を使う。

新形式で分類不能eventまたはcanonical total不一致を検出した場合もbattle決算は失敗させない。影響する内訳・self項目を`null`にし、`completeness`へ原因別件数を保存する。canonical combatを通すfocused testではissue 0を要求する。完全ガードは現行`damage_prevented`へ加えず、受けた側の回数・防止量を別項目にし、自分の攻撃を敵が完全ガードした回数もさらに別項目にする。4.2.1では同じ確定rowから取れる「回復した量／受けた量」「蘇生した回数／された回数」を分ける一方、buff貢献やbarrier付与者別軽減のためのcombat state再設計はDeferredとする。

ジャイアントラットtutorialとリカ命名時storyは現在も必然的にsoloである。旧scripted combatにはDOT/HOT、counter、critical、蘇生、覚醒、完全ガードが存在しないため、対応sourceは確定値としてissue 0で記録する。旧combatが持たないguard防止量とMP統計は0と捏造せず`null`にする。

新規値はcanonical combat resultから決算中に作り、保存済み表示logを後日解析しない。計測はRNG、target、damage、報酬、持越し状態を変更しない。

通常集計の既定対象は`exploration`と`trial`。tutorial、story、playtest、guide duelもactivityを失わず記録できるが、read-only集計では明示指定なしに通常戦績へ混ぜない。

## 3. 旧データの救出

旧battleの既存total、結果、報酬はそのまま正本として保持する。`underground_party_id IS NULL`でsoloと証明できる旧戦闘はtotalとselfが同じ項目だけをbackfillする。これは通常狩場だけでなく、ジャイアントラットのtutorialとリカ命名時のstoryにも適用するが、activityは維持して通常戦績へ混ぜない。PT実装後の旧PTはtotalだけを保持し、self内訳を人数割り・現在build・再戦で推定しない。

旧snapshotの明示値は意味が一致するものだけ救出する。leader覚醒の発動、技使用、portrait eventにある発動round、party人数は抽出候補とする。最大hitやactor帰属を証明できない値は`null`にし、実測0と区別する。統計sourceと記録versionにより新規記録とlegacy backfillを識別する。

明示compactorは既定dry-runで、cutoff、上限、batch、実行時間を必須の境界にする。previewはbatch単位で読み、巨大snapshot集合を一括loadしない。`max-seconds`は各transaction間で確認するsoft budgetであり、lock待ちや実行中の1 SQLを中断するhard deadlineとは表示しない。期限内log、未完了battle、不明形式は変更しない。apply時は1 battleの統計救出、battle/member縮小、検証、version記録を一transactionで行う。再実行はversionでskipし、lock競合または不明行を成功扱いしない。

## 4. Surface audit

新規Turnは次のroutine eventをper-cellで保存せず、既存`turn.summary`へNation×確定Turnで集約する。

- `fire.prevented`: 抽選前に保護対象となったcell数。実際の火災防止回数とは呼ばない。
- `forest.grown`: 成長cell数と増加quantity。
- `population.increased`: 自然増加cell数と実増加人口。人口減少とは分離する。
- `resource.automatic_sale`: requested、sold、revenueがすべて0の行だけ新規記録しない。実売却、売却要求、capacity overflow／破棄の情報は維持する。

旧行は対応するcompleted Turnの`turn.summary`を一意に検証でき、TurnRunの`completed_at`がcutoff以前の場合だけ集約して削除する。一つのTurnRunをevent時刻で分割せず、対象runのsource集合全体を一transactionで処理する。旧writerの`nation_id IS NULL`な`forest.grown`は現在のMapCell ownerから推測しない。同じimmutableな`turn_run_id`をcompleted runへ検証できるrowだけ、turn-run単位のunattributed legacy aggregateへ件数・quantity・provenanceを先に保存してから削除する。そのrunに未帰属森林があるNation summaryは森林値を`null`とし、既知部分と未帰属部分をcoverageで分ける。summaryまたはaggregateへ既に同じcompaction versionがある行は再加算しない。aggregateと未削除sourceが共存する場合はpreviewへ理由を出し、applyは停止する。`command.*`、KARMA、資産移動、moderation、貸出決算auditはこのallowlistへ含めない。

## 5. cleanupと運用

`underground:prune-battle-logs`はbatch size、最大batch数、実行秒数でboundedに繰り返し、logと画像leaseをそれぞれ処理する。開始／終了時の期限切れ件数、最古期限、処理件数、停止理由を出力する。閲覧期限1時間と物理削除時刻を同一視せず、本番cron頻度はこの変更だけでは変えない。

本番apply前に検証済みbackup、空き容量、WAL／更新負荷を確認する。通常migrationは列・reader/writer準備だけを行い、巨大JSONの全件変換やaudit削除を実行しない。削除後の論理保存量、PostgreSQL再利用可能領域、OSへ返るfile sizeを分け、`VACUUM FULL`を既定手順にしない。

`underground:statistics`はbattle IDによるchunk処理で統計JSONとprofile/Secretary identityだけを読む。snapshot・action logを取得せず、Secretary relationのN+1 queryを行わない。既定は件数上限なしの全対象stream集計で、operatorが`--max-rows`を指定した場合だけ、超過時に部分reportを出さず失敗する。各出力項目はrecorded／unknown／not recordedの件数を持ち、既知値が一件もないaggregateは`null`を維持する。貸出秘書はmember別combat統計を保存せず、既存`secretary_lending_participations`を正本としてレンタルされた回数だけをreportする。

## 6. 検証

- solo/PTでtotal/self帰属、barrier、overkill、multi-hit/AoE、回復、軽減、戦闘不能／蘇生、覚醒、MP、action countを代表確認する。
- 同一request再送とrollbackでbattle、統計、drop、貸出ticketが一度だけ決算されることを確認する。
- 期限内詳細と期限後compact履歴、新旧混在readerを確認する。
- compactor dry-run無変更、apply中断・再実行、未知値`null`、台帳不変を確認する。
- Surface集計の合計一致と、戦闘／Turn RNG・gameplay state不変を確認する。
- cleanupが複数batchを処理しつつ上限で止まり、有効log・有効lease・現在画像を削除しないことを確認する。

公開UI、日記帳購入、個室、ranking、地下画面再編は4.3.0側であり、このreleaseでは追加しない。
