# 4.4.0：checkpoint付き30日receipt集約・削除 blueprint

更新：2026-09-21。**設計案・未実装・本番SQL未実行**。
基準コード：`3f49819fb764b5ac2e9fc49f95f6795ded7754d2`。入口：[4.4.0計画](4.4.0-plan.md)。既存依存の地図：[初期調査§6](4.4.0-data-boundary-design.md#6-30日整理残すものと外す依存)。

## 0. Ownerの方式をそのまま目的にする

「○○番までまとめた」を残し、必要な恒久データに集約できたことを確認した後、古い原本を削除する。全request IDを別の無限台帳に移して終わりにしない。30日は目安の保持期間であり、未確定・未集約・必要な参照を消してまで厳密な期限を守らない。

推奨する最初の単位は**profile × source stream**。battle、単発skip、bulk skipはID空間が違うため境界を分ける。貸出参加は受取owner側の単位を使う。テーブル名や列名は仮名であり、この文書からそのままmigrationを実行しない。

## 1. 残すもの／消してよいもの

| 区分 | 扱い |
|---|---|
| 現在資産 | profile、EXP/G/銀行/STP、所持装備、追加強化を保持。集約時に報酬を再決算しない |
| 恒久進行 | trial progress、content clear progress、住宅、女王記念品等を保持。既存の正本を再利用 |
| 生涯統計 | 日誌の対象集合に沿った回数・勝利数・本人damage・unknown件数、skip使用数、貸出累計等を集約 |
| 回想の事実 | 初挑戦、初クリア文、tutorial/命名分岐、初回成長方針を少数の恒久記録へ。必要な既存文章を保持 |
| 詳細log/画像lease | 現行の短い保持期限を維持。receiptの30日とは別 |
| 確定済みreceipt | 集約と出所/再送の依存解消後、保持期限を過ぎたものを削除 |
| 未確定・要修復・未集約 | 消さず理由と件数を示す。範囲を飛び越えて完了扱いにしない |

根拠：`UndergroundJournalService::forUser`、`UndergroundIntroService::projectTrialRecollections/initialGrowthPathKey`、`UndergroundLendingRewardService::settle`、出所migration。[journal][intro][lending][batch-schema]

統計の意味は実装handoffを維持する。旧PT本人分を推測しない、unknownを0にしない。敏捷連撃は1行動・1対象として合計、AoE別対象は別。覚醒変身時全快は回復に含めず、技の実回復は含める。貸出先詳細日記は増やさない。

## 2. 単純なMAX(id)ではまだ安全ではない

### 必須の見落とし防止

**DB一般の仕様**：sequenceの採番はtransaction rollbackで巻き戻らず、欠番があり得る。[pg-sequence]
**そこからの推論**：Aが100を採番して未commit、Bが101をcommitした時に「101まで完了」とすると、後からcommitする100を取りこぼせる。ID順＝commit順ではない。`SKIP LOCKED`で抜かした行があるのに最大IDだけで完了扱いするのも同じ問題。

### 既存IDを使う推奨案の条件

profileごとの排他の下で次を確認できれば、既存のIDを境界として使える。

1. 対象streamの**全writerが、そのprofileのlockを取得してからreceipt IDを採番・INSERTする**。通常battleだけでなくskip、story、playtest、初期化、補修も確認する。
2. 対象sequenceが`CACHE 1`等、後のwriterが以前に予約した小さいIDを遅れて使わない設定であり、低いIDの手動INSERTを通常経路で行わない。live設定は未確認。
3. 集計に使う確定フィールドは、境界確定後に無断で変更されない。後日補修が必要なら集計差分も同じ排他で修正する。

この条件では同じprofileの既存writerがcommitするまでcollectorが待ち、将来の同profile receiptは境界より大きいIDになる。別profileのIDの前後やrollback欠番は、そのprofile内の未集約レコードではないため問題にしない。

**条件が確認できなければ**、既存IDの最大値に無理に意味を持たせない。小さい代案はprofile lock内で発行するprofile別の確定順序番号を使うこと、または処理中のbatchだけ対象ID集合を保存して完了時に消すこと。後者は無限のrequest台帳ではない。ただし飛び越えた未処理行を再候補化する必要があり、最終的に「○番まで」を表示する条件は別に示す。

全Worldを長時間止める汎用compactorへ拡大しない。初回移行時の短い書込停止と、通常運転中の小batchは区別する。採番条件は実装開始時の局所確認で、過去全世代の再現を要求するものではない。

## 3. 最小の保存モデル案

```text
profile側の恒久集計（1 profileに一組）
  battle_count / victory_count
  damage_dealt_known_sum / damage_received_known_sum
  damage_*_unknown_count
  skip_tickets_used
  必要な最大値とその技・対象などの最小情報

checkpoint（profile × streamに一組）
  aggregated_through_id = H
  verified_through_id = V
  deleted_through_id = D     # 連続して削除可能だった範囲だけ
  aggregation_version
  last_batch_from / last_batch_to / 対象件数・集計差分・検証状態
```

仮の列構成。H/Vを同じtransactionで常に確定できる実装なら一本へ畳める。削除不能なpinが残る場合、Dをその先へ進めて「全部削除済み」とは表示しない。最後のbatch情報は上書き/期限付きでよく、全batchを永久保存する義務はない。既存の集計テーブルが同じ意味を持てば再利用する。

貸出の総参加数/繰越余りと日次上限は受取ownerの既存券残高の直列化点へ持つ。戦闘leaderのprofileを保持したまま相互に借用元profileもlockする設計にせず、現在のowner ID順処理と残高lockを利用する。[lending]

## 4. 集約・検証・削除の流れ

### A. 候補選択

一回の実行で基準時刻とcutoff（例えば基準時刻の30日前）を固定する。profileを少数ずつ巡回し、`profile lock → 集計/checkpoint row`の順で短いtransactionを取る。取得範囲を無制限にJSON全読込しない。

Hより後の確定receiptから、上限件数までの**そのstreamの連続した処理対象範囲**を選ぶ。未確定/要修復に出会ったらそこより先へ境界を進めない。単純に`finished_at < cutoff`で抜き出して途中の未確定行を無視する方式にはしない。

日誌対象外の女王等は集計寄与0として分類できるが、「分類不能」を対象外扱いで飛ばさない。完了済みでも回想等に必要な原本は集計だけ先に行いpinして残せる。集計期限と削除期限は別判定にできるが、初版は古い確定prefix中心でよい。

### B. 集計と境界を一緒に確定

擬似コード（APIやtable名を確定した実装ではない）：

```text
transaction:
  profileとcheckpointをlock
  前回のHを読む
  H < id <= B の確定した対象を読み、寄与を計算
  aggregate_before + delta を恒久集計へ保存
  原本の対象件数・既知/未知件数・合計等と保存後の値を照合
  照合できたら H=B, V=B, last_batch=verified を保存
commit
```

集計保存と境界更新を別commitにしない。照合は「足す予定だったから成功」とせず、同じ固定範囲の原本と保存された集計の差分を確認する。数字の列はSQL集約を使い、JSON由来の意味は既存projectorを利用する。全原本のコピーや巨大なhash一覧を恒久保存しない。

不明damageのあるreceiptはknown/unknownの正しい寄与が計算できれば集約可能。不明を理由に永遠に全削除を止めたり、0扱いで成功にしたりしない。真に解釈不能ならその範囲を止めて報告する。

### C. 検証済み原本だけ削除

別の短いtransactionで同じprofile/checkpointを確認し、次をすべて満たす範囲だけ削除する。

- `id <= V`で、原本の所有profile/sourceが一致する。
- 保持期限超過かつ確定済み。active story、参照中画像、未決算・補修中等のpinがない。
- 残すべき装備・ledger・回想・再送情報をreceiptから切り離している。

delete後の件数を照合し、連続した削除完了境界を更新する。途中で止まったら同じ検証済み範囲の削除を続けるだけで、恒久集計へ再加算しない。logが先に期限切れでも、snapshot/receiptの削除が完了したと誤認しない。

一つのbatchでB/Cを同一transactionにまとめる方法も可能だが、検証前に消さない順序と集計/checkpointの原子性は維持する。小規模運用では複雑な二段階commit基盤ではなく、この程度の短いDB transactionで組む案。

### D. 途中終了した場合

| 停止位置 | 次回の動作 |
|---|---|
| 集計transactionのcommit前 | 両方rollback。旧Hから同じ原本を集計 |
| 集計・境界commit後、delete前 | Vまでの削除を再開。集計はHより後だけ |
| delete途中またはcommit前 | 未削除分を再評価。永久集計を再加算しない |
| delete後 | 原本がない範囲を再集計しない。checkpointが復元の基準 |

## 5. 日誌と貸出が二重・欠落にならない読取

移行中を含む日誌は、**恒久集計＋Hより後の未集約receipt**にする案。集約済みだがpin/期限で残したraw行をもう一度足さない。同一応答の集計とHと残りを、一つの一貫したDB snapshot/queryで読む。別々の読取間にcollectorが進み、一方だけ新しい値にならないようにする。[journal]

初回backfillは旧rawから一度だけ集計し、checkpointと同時に確定する。既に恒久counterへ加算する決算コードも同時に動かすなら、境界を明示して重複を防ぐ。初版は「日誌はcollectorで集約」の一方式を推奨し、同期加算と後日加算を無計画に混ぜない。

貸出は日誌とは異なり、**券の付与計算に必要な総参加数/余りを決算時に更新**する。既存COUNT依存を外す時に一度旧値を移し、その切替後はreceiptを消しても10参加ごとの境界と日次上限が変わらないようにする。日誌へ貸出先の詳細damageまで新設しない。[lending]

## 6. CASCADE/RESTRICTと回想の手当て

**確認**：generated装備のsource_battle/skip/batch FKにはCASCADEがあり、券ledgerにはRESTRICTもある。4.3.2のinstance CHECKはgenerated品にいずれかのsourceを要求する。したがってFKだけSET NULLにするとCHECKに反する。[drop-schema][skip-schema][batch-schema][latest-schema]

**案**：所持品自身のpayload/instance_identity/grant_keyと最小の出所情報を保持し、削除可能なreceiptへのlinkを任意化する。出所種別と生成当時の意味を維持するCHECKへ同時に置換。源流を示すID値を残す場合も、生きたreceiptのFKと混同しない。既存のconsumerがsourceの存在を前提に再付与・再生成しないか確認する。

trial progress、女王clear count、Gram取得日時は既に恒久記録なので維持する。回想の「初回」を全historyから再生成する必要がなくなるよう、初挑戦/初クリア文と初回成長方針を先に保存する。現在の成長方針で過去の選択を代用しない。tutorial/特殊敗北の体験flagと、過去battleを開けるかは分離する。[intro][journal]

新しい紋章・魔石・ボス初回clearも同じ方針で、恒久assetを30日receiptのCASCADE子にしない。すべてのFKを外すのではなく、短命の証跡と長命の資産の寿命だけを分ける。

## 7. 古いrequest再送：checkpointとは別に必要

**確認**：現在のUUIDは、receipt/IntroRequestの存在で重複を検出する。UUID自体から信頼できる期限は得られない。`H=500000`を持っていても、外から再送された古いUUIDが削除済みID499999だったとは判定できない。[runtime][intro]

**推奨候補（Owner精査が必要）**：新規の更新要求に、サーバーが発行したprofile・request ID・操作区分・発行/期限に結び付く署名付き受付情報を使う。署名対象のIDはサーバー生成とし、クライアントが任意の古いUUIDを新期限で再署名させるAPIにしない。request_idを含む既存fingerprint/認可を捨てず、受付期限だけを小さく加える。

同じ操作の再送は同じ受付情報を使い、保存結果があれば返す。期限切れで原本もない時は「受付期限切れ」とし、新規として消費/報酬を再実行しない。ブラウザが自動で新しいID・tokenを取り直して同じ操作をretryしてはならない。新たな意思による操作だけ新しい要求にする。

移行案：新形式の受付を先にdeploy→旧形式の新規受付終了時点を定める→必要な保持期間中は旧保存結果を返す→依存整理と集約が完了した範囲からpurge。削除開始後も旧形式の未知UUIDを無条件に受け付け続ける設計にはしない。

追加HTTPを毎戦必須にするか、既存state応答で有限個の受付情報を供給できるかも実装時に評価する。署名方式以外の小さい同等案も可。受付期限・旧タブ/旧clientへの説明・clockの基準は未決。これが決まるまで原本purgeだけを有効にしない。全UUID永久保存や新しい汎用ジョブ基盤は要求しない。

## 8. 実装・稼働前の確認順

1. 現行writer/sequence/参照FKと、集計対象集合をread-onlyで確認。実際の本番値をrepoだけから決めない。
2. 恒久保存先とreaderを準備。旧値を保持するmigration/backfillの代表を確認。
3. 受付契約を移行。集約のみ動かして結果を照合する。まだdeleteしない段階を用意する。
4. profileごとの小batchで、集計+checkpoint+削除を中断・再実行する代表を確認。
5. Ownerが本番適用を許可してから開始。件数/停止理由/境界を報告し、容量改善を実測する。

代表で確かめるのは、途中終了後の一度だけ集計、遅延commit/飛ばした行の取りこぼし防止、装備と試練/女王記録・日誌の保持、貸出の余り、期限後再送の再決算拒否。同じ故障の全組合せは作らない。既存routine compactorレビューの「一部集約で全体完了扱い」再発を避ける。

本書は既存DBを削除するSQL、scheduler、VACUUM FULL、バックアップ再実行を提供するものではない。4.2.1の固定cutoff作業は完了済みで再applyしない。まず新しい境界と移行だけを実装し、削除は確認後に切り替える。
