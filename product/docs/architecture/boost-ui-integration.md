## #332で必要な表示調整

`App.vue` のターン欄は、開催中の `turn_interval_minutes:60` だけを見て「時間加速中：60分ごとに更新」と表示する。しかしサーバーの時間加速は **通常のJST偶数時00分＋期間内の奇数時00分に未補填分だけ追加** であり、未補填がなくなれば奇数時を実行しない。停止中も実行しない。開催期間が残っているだけでは毎時更新を保証しないため、そのままの統合では誤表示になる。

#332側では、例えば「停止補填中：奇数時にも追加（未補填分のみ）」と表示し、次回時刻は既存の `worldSummary.next_scheduled_turn_at` を使う。`turn_interval_minutes` から次回時刻を計算しない。`effects.compensation_only:true` を型へ追加して表示分岐するか、今回の `turn_acceleration` の意味を固定して扱う。`BoostBanner.vue` はAPIの `description` を優先しており、こちらには未補填条件を既に含めている。狩場descriptionもG・鍵の個数は増えないと明示する。

サーバー応答の `turn_interval_minutes:60` は奇数時を追加できる期間の名目的な間隔であり、無条件の実行契約ではない。公開APIは各種別の開催中または次回を1件返す。#332は5分ごとに再取得するため、管理室取消から表示への反映は最大約5分遅れることがある。表示の遅れは効果の適用可否に使わず、サーバー受付時の判定を正本にする。タイトルとdescriptionはplain textで表示する。

このTOP表現の調整は#332側の残件として明示する。#334から相手branchを書き換えない。調整前の両PRを組み合わせた結果を「誤表示なし」とは扱わない。

作業用の別worktreeに#334の変更と上記固定HEADの6ファイルを重ねる。実公開API応答をrollback付きで採取したfixtureと#332の取得関数・帯を接続する。さらに#334の管理室操作テスト、型検査、ESLintを実行する。いずれもshellから行い、ブラウザー・画面・既存3D制作環境を操作しない。

管理室実装HEAD `d340370da20ee22d3757062d3bb9e616b303a2fc` と#332固定HEADの統合状態で、管理室・既存管理操作・公開帯・実API接続の計12件が成功した。うち1件は実際の `App.vue` をmountし、TOPには「60分ごと」、帯にはAPI descriptionの「未補填分」が同時に表示される不一致を再現した診断である。この1件の成功を誤表示の解消とは扱わない。その他の管理室6件は、JST送信・プレビュー後の明示予約・通信断時の同一token再送・一覧更新の失敗分離・409後の再プレビュー・取消範囲固定を確認した。統合状態の型検査と関連ESLintも成功した。

最終のテスト結果と固定HEADは#334本文で追跡する。管理室の予約試験はモック／専用隔離DBに限り、実イベントを予約しない。片方だけでも基本画面は動くが、公開帯を含む機能の統合には両PRが必要。TOPの補填条件の修正後に公開表示を再確認する。
