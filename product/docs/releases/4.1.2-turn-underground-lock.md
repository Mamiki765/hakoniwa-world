# 4.1.2 Turn・地下PT lock hotfix

## Release boundary

- Base SHA: `764beb4cfb595e293a067368cef87993253cd9f1`
- Application version: 4.1.2
- Migration: なし
- Ruleset変更: なし

## Production incident

Owner提供の記録では、Turn478 attempt 1が`finalize_turn`中のPostgreSQL `40P01`で失敗した。Ownerは同じTurn・Ruleset・seedでattempt 2をmanual retryし、Turn478の完了を確認済みである。追加recoveryは不要で、このhotfixではproduction操作を行わない。

発生した待ち合わせは次の形だった。

```text
Turn finalize
  borrowed SecretaryをFOR UPDATE
  -> leader Secretaryを待つ

Underground party snapshot
  leader SecretaryをFOR NO KEY UPDATE
  -> borrowed Secretaryを参照するparty member INSERTのFK KEY SHAREを待つ
```

TurnはSecretary ID昇順でbatch lockする。一方、地下PTはleaderをlockしたtransaction内で、より小さいIDの借用SecretaryをFK参照し得る。この逆順が2-way cycleを作った。

## Fix

`SecretaryTurnService::flushExperience()`のSecretary本体batch lockを`FOR UPDATE`から`FOR NO KEY UPDATE`へ変更する。この処理がSecretary本体で更新するのはnon-key列の`monster_experience`だけである。

`FOR NO KEY UPDATE`は、同じSecretaryを更新する`FOR UPDATE` / `FOR NO KEY UPDATE`とは競合するためwriter間の直列化とlost update防止を維持する。一方、party member INSERTが外部キー確認に使う`KEY SHARE`とは共存するため、Turnが借用Secretaryを保持したままleaderを待っていても地下側が借用SecretaryのFK確認を終えてcommitでき、cycleが切れる。

Secretary skill EXPは`secretary_skills`を従来どおり個別に`FOR UPDATE`する。Undergroundのprofile・equipment・skill snapshot lock、FK、同じSecretaryを使う地下操作のserializationは変更しない。4.1.1で修正したお問い合わせとTurnのlock共存も維持する。

## PostgreSQL regression

別connection・別workerで、次の順序を固定するfocused testを追加する。

1. 地下PT workerがleader Secretaryとleader profileをlockする。
2. Turn workerが小さいIDの借用Secretaryを保持し、leader Secretaryで実際にblockしたことを`pg_blocking_pids()`で確認する。
3. 同じ借用SecretaryへのwriterもTurn workerでblockすることを確認する。
4. 地下PT workerを進め、party snapshot、Turn flush、並行writerがすべて完了することを確認する。

修正前の同fixtureではparty member INSERTが`40P01`となり、修正後は双方が完了した。Turnのskill EXPとmonster EXP、party member、並行writerの加算結果も検証し、lost updateがないことを確認する。

## Central facility quantity

中央銀行・中央穀倉はAPIで`quantity_semantics=ordinary`として投影され、frontendの汎用quantity editorを使用する。executorでも両commandは共通のquantity継続経路に入り、成功ごとに1減って同じセルの施設を新設・増設する。別セルへ同種中央施設を作る場合は既存の1Nation 1施設制限で拒否される。

現行codeと既存testで意図した挙動を満たしているため、この確認によるcode・test追加は行わない。
