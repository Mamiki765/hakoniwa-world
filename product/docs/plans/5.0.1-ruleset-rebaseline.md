# 5.0.1 適用後の Ruleset / database rebaseline

## 承認済みの境界

固定基準は `5affee61f180d6766ff7e59ce275c304c54002ad`（5.0.1）。Owner提供画像について、
引継ぎでは本番5.0.1、T802正常、Ruleset v36 / id51、pending migration 0を確認済み。
Ownerは5.0.1を新基準とし、以前の環境からの直接更新を終了する方針を承認した。
対象本番は一つで、現在のデータ保持と新規構築を検証の中心とする。

5.0.1より前の環境は、対応する固定旧版codeで先に完成した5.0.1へ到達させる。
このtreeへ旧migrationを戻したり、現行値から旧snapshotを再公開したりしない。
この作業はローカル実装と隔離した合成DBでの検証であり、本番DBを再検査・変更していない。

検査する。旧v27〜v35 entrypointとrelease fragment、使用終了したpublication helperは撤去し、
実装の由来はGitへ残す。DBに保存済みのsnapshot、definitions、ID、履歴参照とその読取処理は維持する。

application version、Ruleset key、番号、全payloadの値・型・キー順・list/map・空配列は変更しない。
v36 checksumは `bbe3b65812bf337da0617577b38528a6583439bd9d672efe83cf67b249004308`。
完全payloadと17 domainのclassificationは固定基準の解決済みsourceと厳密に一致する。

## 新規構築と既存採用

`database/schema/pgsql-schema.sql`は固定5.0.1の15 migrationを完了した隔離PostgreSQL 18.4から
取得したschema-only dump。ledger、業務行、sequence現在値、owner/ACL、MCP所有schemaは含めない。
新規構築はこのdumpと`2026_10_11_020000_install_5_0_1_baseline`の1 migrationで完成する。
現行catalog、v36 snapshot、初期merchantだけを作り、過去世代の公開や完了済み補填は再生しない。

既存採用は`CurrentDatabaseBaseline::assertExisting()`で完全な構造、5.0.1の必須15 ledger名、
現行catalog、保存済みv36 payload/definitions、共有Worldのv36参照を検査する。
成功時の業務処理はread-onlyで、Laravelが採用markerを1件追加する。旧ledgerのID/batchも残る。
国・秘書・地下資産・queue・TurnRun・event・audit・published ID/FK・sequence現在値を変更しない。
追加schema、診断view、owner/ACLも採用処理のDDL/DML対象にしない。

ledgerなしのDBは全業務tableが空の場合だけ初期化する。未知構造や未完了5.0.1は停止し、
自動修復・reset・補填をしない。`down()`はforward-onlyとして拒否する。

## 完全な構造 manifest の由来

`5_0_1_structure.json`は各179 objectを完全一致で検査する。列の順序・型・default・nullability、
constraint、index、trigger、sequence定義、public functionを削らず、比較時に正規化しない。
既知の列順とCHECK式のPostgreSQL表現差は、次の完成構造を独立した完全集合として記録する。

- `upgraded_5_0_1`: 固定5.0.1 codeの通常fresh→15 migration完了。
- `restored_5_0_1`: 保存済み本番4.9 schema-only fixture→固定5.0.1 migration完了。
- `production_5_0_1`: 保存済み本番4.9定義の全176 hashを旧正式manifestと照合し、上記で
  観測した固定5.0.1のDDL変更だけを反映。変更しないCHECK表現などは元の定義を保持する。
- `fresh_5_0_1`: 新しいschema-only dumpを空DBへ復元した構造。

`production_5_0_1`は保存済み証跡と固定DDLからの導出値で、現本番5.0.1を直接読んだ測定値ではない。
実運用への適用前には、本番でread-onlyの`php artisan hakoniwa:baseline:check`を成功させる必要がある。
不一致時はそのobject差分を確認する。推測で受入variantを増やしたりDBを変更したりしない。

## 検証と残る運用確認

固定5.0.1を実行した隔離DBへ、国・秘書・地下XP/欠片・保護装備・pending queue・保存済みv28と
そのWorld/TurnRun・別schemaの診断viewを作り、採用前後を比較した。86業務tableの1606行と
80 sequenceの状態は一致し、旧ledger15件をそのまま残してmarker1件だけを追加した。
再度migrateしても無変更。新規構築のWorld、国、command、turn、秘書item初期化もfocused testで確認した。

既存のfresh/adoptionテストを現行境界へ更新する。旧版へのschema巻戻しや過去migrationの再生ケースは
撤去し、保存済み履歴の解釈・現在のDB制約・資産保持の保証を残す。別taskの大規模テスト棚卸しには触れない。
Ruleset不変性、構造/ledger drift拒否、保存履歴の解釈と現在の装備/国名保証だけをfocusedに実行する。
全suiteはexact-head CIの対象とし、ローカルでは回さない。具体的な実行証跡はこの作業域のqa/evidenceへ保存する。

本番のread-only採用check、backup検証、実運用migration、deploy、mergeは今回の範囲外で、未実施。
既存データに対して`migrate:fresh`やschema dumpの直接読込を行わない。
