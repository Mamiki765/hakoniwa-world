## 0. 実装担当が最初に読む要約

- 所有関係 `User → Secretary → UndergroundProfile` は維持する。島の作り直しで秘書・地下進行を失わせない。ロック隔離のために地下をNation所有へ変更したり、User行を毎戦の新しい共通ロックにしたりしない。
- 地上Turnは経験値flush以外にも、怪獣ドロップ、埋蔵宝回収、交易場のアイテム配送で `secretaries FOR UPDATE` を取る。`monster_experience`だけの分離では足りない。
- 地下は戦闘だけでなく、ホーム取得、装備一覧・ショップ取得、初期装備の補完、貸出設定にも親Secretaryのロックがある。入口をまとめて見直す。
- 推奨案は、地上の可変状態・在庫の直列化点を地上専用行へ、地下の直列化点を既存profileへ寄せること。identityのFKや既存の地下テーブル群は基本維持する。
- Turn560の相手側SQLは未取得。前半で取得した強いロックがfinalizeまで残る循環を、最初の再現候補H1とする。確定した本番原因とは呼ばない。
- Turnの限定retryは別の改善軸。同じrun内のtransaction retryだけでは、全attempt失敗後の「次回cronも永久拒否」は残る。二段階を区別する。
- 試練・女王のクリア判定と既存トロフィーは、既に恒久記録を利用している。30日整理で重点的に外すのは、資産の出所FK、貸出累計、日誌集計、回想、古いrequestの再実行依存。
- 次の着手は§3〜5のロック修正範囲決定。§6の削除は依存整理後。ボス等の最新Owner案は§8に保存し、未決事項を実装者が補完しない。

## 2. 既存の所有関係と分離対象

**確認**：[Secretary model][identity]、[profile作成migration][profile-schema]。Secretaryは`user_id`を持ち、profileはuniqueな`secretary_id`で紐付く。地下profileにはNationの所有FKを置いていない。

```text
User
 ├─ Nationへのmembership → Nation・地図・Nation地下施設
 └─ Secretary（島とは別の永続identity）
     ├─ 地上：monster_experience / equipment_version（現在は親行）
     ├─ 地上：secretary_skills / secretary_item_instances
     ├─ 表示：名前・紹介・画像／secretary_images
     └─ UndergroundProfile
         ├─ LV・EXP・G・銀行・STP・HP・覚醒・レンタル状態
         ├─ 地下装備・技能・試練進行・コンテンツ別クリア回数
         └─ battle / skip / intro request等の記録
```

`UndergroundFacilityBenefits`が扱う`nation_underground_facilities`は、地下RPGの装備・LVとは別の**Nation施設**。Turnはここから施設効果を読む。「undergroundという名前だから全てUser所有へ移す」ことはしない。[施設bridge][facilities]

**提案**：既存profile ID、secretary ID、userとの経路は維持する。`underground_profiles.user_id`の重複追加や別の地下Userを作ることは、今回のロック分離の必須条件ではない。認可は必ずログインUserから所有関係を辿り、受信したprofile IDだけで更新しない。

## 3. ロック接点の実測前インベントリ

表は主要な取得順の抜粋であり、各transactionの全ロック一覧ではない。`UPDATE`は`lockForUpdate()`、`NKU`は`FOR NO KEY UPDATE`を表す。

|---|---|---|

| `SecretaryTurnService::loadAttemptSnapshots` | owner membershipから秘書・地上技能・装備を通常読取 | snapshotの取得元を新しい地上状態へ揃える |

### 3.3 H1：4.1.2の修正後でも残り得る循環

**確認**：4.1.2はflushのSecretaryロックをUPDATEからNKUへ弱め、party member INSERTのFK確認と共存させた修正だった。[当時の記録][old-fix]

**推論**：Turn前半のdrop/treasure/配送が取得したUPDATEは、helperから戻っても外側Turnのtransaction終了まで残り得る。後のflushで同じ行をNKUで読んでも、既に保持する強いlockを解除する操作ではない。[PostgreSQLのロック仕様][pg-lock]

```text
Turn                                地下PT
前半に秘書AをUPDATEで保持
                                    leader秘書BをNKUで保持
finalizeで秘書Bを待つ
                                    party member作成で秘書AのFK KEY SHAREを待つ
→ 循環。finalizeのSQLにはNKUとだけ表示されても、Aには前半の強いlockが残る
```

これは本番Turn560の再現を証明したものではない。しかし「flushの1行だけ見る」「ORDER BY idをもう一度足す」より先に調べるべき具体的経路。既存の4.1.2競合fixtureに、flush前の実grant/配送相当の強いlockを加える代表再現を推奨する。

**以前の会話説明の訂正**：`KEY SHARE`と`NO KEY UPDATE`は互換。identityのFKがあること自体を理由に、User-root化・別DB化が必須とは言えない。問題は取得するmodeとtransaction全体の順序である。[pg-lock]

## 4. 分離の設計案

### 4.1 推奨する最小構成

```text
secretaries                      identity / 表示。通常周回の排他起点にしない
 ├─ secretary_surface_states     新設候補：monster_experience / equipment_version
 │   └─ 地上在庫・装備更新の直列化点（既存items/skillsは基本維持）
 └─ underground_profiles         既存：地下状態・G・成長・装備操作の直列化点
```

テーブル名は提案。地上状態は`secretary_id`ごと1行で、Nationの削除に連動させない。初期値を既存親行からそのまま移し、秘書や地下profileを作り直さない。

**地上側の変更単位**：経験値だけでなく、§3.1の在庫grant・配送・装備version更新を同じ境界へ揃える。親の`monster_experience`を移しても`equipment_version`を書き続けたり、共通grantだけが親をlockし続けたりすると分離が中途半端になる。

`SecretaryProfilePresenter`、`SecretaryTurnService`、`SecretaryEquipmentService`等の読取／API投影も移す。API上の`monster_experience`・`equipment_version`の意味は維持してよく、DB移動だけでUIに新しい所有IDを要求しない。

既存`secretary_skills`・`secretary_item_instances`の全列を新テーブルへ詰め直す必要はない。容量・slot・所有・二重grantを守る排他の起点を一つに揃える。

### 4.2 地下側の変更単位

- 通常の既存profile操作は、ログインUserに属するprofileを確認してその行をlockする。Secretaryはidentityの読取・FKとして残す。
- JOINで対象を絞る場合も、単に`lockForUpdate()`を付けて親までlockし直さない。必要ならPostgreSQLの`FOR UPDATE OF p`のように対象を明示する設計を採る。
- 初回profile作成は行がまだないため別扱い。既存unique制約を使った作成競合処理と、作成後の同一profile lockを揃える。全操作を無lock化しない。
- 借用元snapshotを準備する短いtransactionと、本戦transactionの分離は維持する。借用元の全profileを戦闘終了まで抱え直さない。
- 貸出設定更新、装備変更、snapshot採取が同じprofile/子rowの順序を使うよう揃える。画像差替え・保持leaseも調査対象に含める。
- ホーム・装備GETで行うstarter補完は、初期化側への移動か、必要時だけの短い補完へ寄せる案。正常取得で長い親lockを取らないが、不足装備の回復機能を勝手に捨てない。

`UndergroundProfileService`を小さく拡張するなど既存の入口を使う。全ドメイン共通の汎用lock frameworkや、新しい地下専用認証基盤は不要。

### 4.3 User・画像・地上への橋を取り残さない

`VisitorCodeAllocator`は発行済みでもUserをlockする。既存codeの読取と未発行時の初期化を分けられるか確認する。ただしidentity発行の一意性・認証との整合性は残す。

`SecretaryImageRetentionService`は借用snapshot準備時の画像leaseと、battle確定後の昇格を扱う。親lockを削るだけで、snapshot採取と画像削除の間に穴を開けない。画像の短いlock／leaseは必要な範囲で維持する。[画像保持][images]

`DailyQuestService`、`UndergroundLendingRewardService`等が使う日課・Pd・チケット残高は共有の報酬境界として残る。`users`へ排他を集約するのではなく、既存の個別残高・進捗rowで直列化する。貸出先の順序も確認する。

地上→地下の新報酬は後述の構想。Turn内で全員の地下profileをlockしてGや強化を配る設計を追加すると、今回切った境界を再接続する。将来必要なら、既存配布等による明示的受取を第一候補に検討するが、今ここで新outboxやworkerを作る指示ではない。

### 4.4 移行の進め方

必要なschema追加、既存値のbackfill、consumer切替を一つのrelease移行として設計する。既存ID、Userとの対応、EXP、G、STP、装備payloadを保持する。旧列を残す場合も二つの書込正本を永久運用しない。

4.3.2までの適用済みmigrationを書き換えない。ここで履歴全体のsquashや全旧世代テスト復活を追加しない。4.4.0のmigrationの具体本数・適用順は変更範囲が決まってからまとめる。

## 5. Turnのdeadlock耐性

### 5.1 現在の動作

`TurnRunner::execute`は本体を`DB::transaction(..., 1)`で実行する。失敗すると外側でrunをfailedにする。`prepareRun`はfailed/blockedへのcron再実行を拒否する。記録するfailure_contextはphaseとexception_classで、SQLSTATEの独立した項目はない。[turn]

World advisory lockはsession単位で、Turn transactionの外側から保持される。[WorldMutationLock][world-lock]

### 5.2 提案A：同じ呼出し内での限定retry

対象をPostgreSQL `40P01` / `40001`へ限定し、例えば初回を含む最大3attemptまでTurn本体transactionをやり直す。未知例外・制約違反・Ruleset不一致・commit成否が不明な切断を同じ扱いにしない。[PostgreSQLのretry仕様][pg-retry]

再試行では、同run/target/ruleset/seed、Worldの再検証、新しいTurnContext/TurnState/RNGを維持する。後半phaseだけの再開や、エラーSQLだけの再送はしない。並行更新が入り得るため、「同seedだから全入力・結果が前attemptと完全同一」とは説明しない。

**`1→3`だけで安全確認済みとはしない。** Contextはcallback内で作り直されるが、phaseの依存サービスは再利用される。

- `CompleteTurnEngine`にrun IDをキーにしたdefinition cacheがある。immutableな定義cacheと、失敗前のゲーム状態cacheは区別する。
- `MonsterRemovalService`はbatch・削除数を保持し、run ID / World ID / attempt_countでbatchを選ぶ。内部transaction retryではこの3つが同じなので、reset/再構築が適切な時点で必ず通るかを確認する。[実装][removal]
- 新attempt開始時に必要なmutable stateだけをresetするか、該当インスタンスを再生成する。静的定義まで全部捨てる義務にはしない。
- `attempt_count`は現在runの再実行回数。内部transactionの回数を黙って同じ値へ混ぜず、既存failure_contextやログへ区別して残す。SQLSTATEは構造的に記録する。

### 5.3 提案B：全attempt失敗後もOwner待ちだけにしない

提案Aだけでは、3回失敗すると今までどおり次回cronも拒否する。Ownerの「不在で一過性競合のため永久停止しない」を満たすには、次の起動時の方針も必要。

候補は、構造化して記録されたretry対象SQLSTATE、同じtarget/ruleset、実行コードの互換性を確認できる場合に限り、次の起動で同runを再試行すること。blocked、不明なエラー、stale-runningの自動回収は一緒に許可しない。

最大回数／待機／通知、コード変更を跨がない識別方法は未決。まず同一プロセス内のAを先に実装してもよいが、その段階を「永久停止問題も解決」と報告しない。cronを単純な`--source=manual`連打に置き換えない。

既存D-02は初期公開時の自動retry禁止で、backoff等を公開後TODOとしている。実装時にはこの変更を明記して整合させる。Ownerは見直しを希望しているが、このメモが未決のretryポリシー全てを承認したことにはしない。[設計索引][gates]

根拠：[日誌][journal]、[貸出決算][lending-reward]、[回想／initialGrowthPathKey][intro]、[生成装備migration][drop-schema]、[skip migration][skip-schema]、[bulk skip migration][batch-schema]。

**資産について特に重要**：4.3.2の`underground_owned_equipment_instance_check`はgenerated品に出所battle/skip/batchのいずれかを要求する。FKだけ`SET NULL`へ変えると、このCHECKと不整合になる。削除許可・出所保持・CHECK置換を一緒に設計する。[4.3.2 migration][latest-schema]

提案は、所持品自身に必要最小限の出所情報を保持し、閲覧用の元receipt参照を任意にする方向。全receiptを別名の無限台帳へ移すだけにはしない。既存の生成payload/sourceやgrant identityを使えるか先に確認する。

UUIDには現状、信用できる発行時刻を必ず判定できるという契約がない。単に「30日前の行を消す」だけでは、古い再送と初めて届いた要求を判別できない。期限付き受付等の小さい契約を次に選ぶ必要がある。未決の間は現行の詳細log整理だけを維持し、receipt purgeを開始しない。

`pruneExpiredBattleData`が現在消すのは期限切れlogと画像参照。1時間の詳細保持、snapshot圧縮、30日receipt整理、恒久記録は別工程である。[runtime]

## 7. 次に必要な確認と実装の小分け

### 7.1 未取得データ

- 本番Turn560 deadlockの**両側SQL**、発生時のtransactionと処理入口。アプリ側の一方の例外だけでは確定できない。
- 稼働PostgreSQL版・実際のFK/trigger・migration適用状態。repositoryのschema dumpをlive schemaと同一視しない。
- 主要共有テーブルとreceiptの件数・容量・増加速度。G大量所持はOwner報告で、本調査で全ユーザー残高を読んでいない。
- 地上item売却／使用／交易出品、秘書プロフィール・画像更新、アカウント削除、追加consumerの全lock順。今回の表は主要経路の初期版。
- Turnのmutable cacheの全入口、transaction外の副作用。新attemptで初期化済みかは実行確認が必要。

調査用SQL例（読取のみ・未実行。稼働環境を確認したoperatorが必要な時だけ使用）：

```sql
-- 現在待機しているtransaction。過去のdeadlockはサーバーログから採る。
SELECT pid, application_name, xact_start, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blockers, left(query, 1200) AS query
FROM pg_stat_activity
WHERE datname = current_database()
  AND pid <> pg_backend_pid()
  AND (wait_event_type = 'Lock' OR cardinality(pg_blocking_pids(pid)) > 0)
ORDER BY xact_start;

-- 削除対象へ向くFK。CASCADEとRESTRICTの両方を確認する。
SELECT conrelid::regclass AS child_table, conname,
       pg_get_constraintdef(oid) AS definition
FROM pg_constraint
WHERE contype = 'f'
  AND confrelid IN ('public.underground_battles'::regclass,
                   'public.underground_skip_settlements'::regclass,
                   'public.underground_skip_batches'::regclass)
ORDER BY 1, 2;
```

query本文にはユーザー入力等が含まれ得る。必要なSQLだけ切り出し、credentialや無関係なログ全体を共有しない。調査のため本番で競合を再現したり、sessionをterminateしたりしない。

### 7.2 推奨する順序

1. **H1と変更範囲の確認**：§3の親lockをcaller＋helperで追い、既存競合fixtureで代表経路を確認。
2. **ロック境界切替**：地上state・地下profile・snapshot入口を揃える。島再作成時の所有関係と既存資産は維持。
3. **Turn限定retry**：mutable stateの再初期化を確認して提案A。提案Bは別の運用判断として明示。
4. **恒久化と出所分離**：既存の進行保存先を活用し、日誌・貸出繰越・回想・装備参照を整理。
5. **受付期限とpurge**：再送の意味と集計方式を決めてから、既存のbounded cleanupへ組み込む。
6. **異世界ボスと新強化**：整えた地下境界へ載せる。恒久実績と報酬の保存を最初からreceipt依存に戻さない。

この順番は提案。全てを巨大な1PR・1回の作り直しにする義務ではない。ロック改善とボスの戦闘調整は並行可能。

### 7.3 確認の最小セット

- 既存`InquiryConcurrencyFailureTest`のTurn/party代表を活用し、前半の強いlockを含む経路を確認。全組合せの恒久テストは作らない。
- 同じ地下profileの戦闘と装備/G操作は排他され、別人の通常周回と地上Turnは不要な親writer lockを取り合わないこと。
- 後半で失敗する代表からのretryで、EXP・item・eventの二重適用やbatch残存がないこと。未知例外は再試行しないこと。
- supported直前状態からの移行でID・所有・資産・達成済み状態を保持。fresh installも現行schemaに到達。
- purge実装時は、所持品・試練/女王実績・日誌・貸出繰越を保持し、再実行で集計が増えず、古いrequestも再決算しない代表を確認。

小修正ごとのFull反復、旧全世代の再現、件数維持のための代替テストは不要。今回はテストを追加・実行していない。

### 8.3 装備／技能／LVと別軸の強化・G消費

Owner意向：100万〜1000万近いGの使い道にもしたい。低ランクを揃えて中級1攻略を目指す。候補はマテリア的魔石、エンチャント、アクセサリーとは別の指輪枠。方式、slot数、移し替え、強化成功率、価格、消費通貨の引出方法は未決。

ここでいうGは地下の`shard_balance`／`banked_shard_balance`であり、地上Nationの億円残高とは区別する。所持金を減らす移行・資産リセットを意味しない。

設計上の提案：方式未決の間は新DBを先行作成せず、採用後は地下profile所有の状態として持たせる。恒久強化をbattle receipt配下に置かない。装備交換のたびに同じ強化を全部作り直す方式にするかは、金の消費量だけでなく装備更新の楽しさと一緒に決める。

### 8.4 IL拡張で調べる具体箇所

`product/config/underground-equipment.php`のgenerator上限とbody_anchors、`UndergroundRuntimeEquipmentGenerator::interpolate/sellPrice/rollAffix`を一緒に確認する。4.3.2では上限と補間点がIL120までで、範囲外は外挿しない。売却価格にも120までの別anchorがある。

割合系affixのIL倍率は`min(20_000, 10_000 + (($itemLevel - 1) * 100))`で101以降頭打ち。IL上限だけ210にしても、この性能は伸びない。HQとレリックはaffix枠数も違うので、数字のILだけで120理想品を超えたと判定しない。

LV・他部位・技能・AIを固定し、武器交換による実効火力／回復量を比較する。4つの試験LVと前段階強化で、役割が働くかを見る。FF14のIL刻みの模倣や前回答の仮倍率は、箱庭の確定仕様ではない。
