## Owner確定の保持境界

個別raw履歴・任意期間統計は30日超で削除可能。資産、Trial/content clear/trophy/residence等の恒久progress、生涯統計、貸出累計、回想の初回事実は保持する。
月別・日別の恒久bucket、全receiptの縮小コピー、全UUIDの永久台帳は作らない。

## D2：恒久依存

追加migration `2026_09_22_010000_detach_durable_underground_receipt_dependencies` はforward-only。

- generated装備の三つのsource IDは値を保持した出所記録へ変更し、receiptへのFK/CASCADEを外す。source種別は非NULLの列で一意に決まり、既存instance CHECK・unique・grant key・生成payloadを維持する。正のsource IDとskip reward indexの存在も検証する。装備は再生成・再配布しない。
- 貸出累計は既存`user_skip_ticket_balances`の`lifetime_participation_count`へ一度backfillする。同じ残高ロック内で参加ごとに加算し、10回境界・日次100枚上限・券残高を維持する。他ownerのprofileはlockしない。skip券ledgerのskip/batch FKはSET NULLへ変更し、entry key・差分・残高・日付は残す。
- introのtutorial/scripted-loss IDも恒久的な経験の根拠として保持し、rawへのFK/CASCADEを外す。既存stage/branch/CHECKはそのまま使う。tutorialのencounterと最初のgrowth pathを保存し、最初のgrowth requestのfingerprintからのみbackfillする。現在のgrowth pathで補わない。
- Trial初挑戦時刻・導入文・初clearの文章snapshotは既存`underground_trial_progress`へ追加する。初clear日時・解放・報酬の正本は変更しない。初挑戦の判定と回想readerのraw検索を廃止する。
- 日誌に不足する本人とPT合計の生涯統計はD1の同じrollup行へ集約する。heal、guard、防御、撃破、技使用、MP、覚醒等の既存指標、最大一撃と技/source、source別内訳、不明件数・理由を保持する。D1にある本人damage合計は重複保存しない。最低/終了HP等の一戦の瞬間値は生涯合計にしない。
- 詳細統計は既存projectorの確定結果を足し、combatを再計算しない。known sumとunknown件数を分け、最大一撃は既存の1 action・1 target値を比較する。D1で集約済みのprefixにも一度だけ不足統計をbackfillし、以後は同じcheckpoint transactionで保存・読み返し照合する。

D2ではreceiptの削除入口を作らない。migrationは通常の書込停止を含むrelease手順で適用する。本番への適用・purgeは今回実行しない。

## D3：24時間受付

- `/api/v1/me/underground/requests` はprofile・HTTP operation・server生成UUID・issued/expires・形式versionを認証付き暗号tokenへ束縛する。指定UUIDの再署名は受け付けない。既存receiptのrequest ID/fingerprint/idempotencyは維持する。
- 地下mutationはtokenが必須。旧タブ/旧形式はdeploy直後から409と再読込案内で拒否し、grace periodは設けない。read-only bulk-sell previewは対象外。
- 発行endpointは独立したthrottle prefixを使う。受付取得が既存mutationのrate limitを追加消費しない。
- 24時間超は保存結果がある場合だけ既存のretry経路へ渡す。結果がなければ決算前に拒否する。入口と既存profile lock直後で期限と結果の存在を確認し、purgeとの競合でも再決算しない。新たな他owner profile lockは追加しない。
- ブラウザの操作IDは一時的なintent keyとしてのみ利用し、送信UUIDはissuerの値を使う。同じ操作の通信失敗/retryでは同じtokenを保持する。期限切れを受けたページは再読込までmutationを止め、token再取得による自動再実行をしない。
- 既存gameplay testはサーバ発行済みの受付fixtureを共通adapterから渡す。受付契約testはadapterを無効にして実issuer・middleware・決算を通す。

D3 focused: backend 12 tests / 546 assertions、frontend 5 files / 45 tests。変更PHPのPint/PHPStan、frontend typecheckと変更ファイルlintも確認。Full PHPUnitは最終D4 HEADのQualityへ委譲する。

## D4：手動purgeとread-only status

追加migration `2026_09_22_020000_add_underground_receipt_deletion_checkpoints` はforward-only。
同じrollupに`deleted_through_id`・削除累計件数・上書き型の最終削除batchを追加し、DB CHECKで`0 <= deleted_through_id <= verified_through_id`と削除件数上限を保証する。
IntroRequestも独立streamとして集計/削除境界を持ち、battleからのCASCADEはSET NULLへ変更する。
中間D2環境の既存prefixは、未削除rawからPT合計を一度補完する。D1からの通常upgradeではD2 migrationで同じ統計をbackfillする。

削除はprofileの既存serialization lock内で、ID順の連続prefixを最大1000件まで処理する。完了から30日を超え、verified境界以内、準備済み、恒久統計/初回事実が保存済みのものだけが対象。
進行中Trial、導入story、未失効の詳細log/画像leaseによるpin、統計の補修・準備待ちで停止する。後ろの行を飛び越えて境界を進めない。rawの完了時刻はDB NOT NULLであり、writerは決算全体をtransaction内で作成する。未確定writeはprofile lockで待ち、NULL完了時刻にもfail closedする。

battleの貸出参加・party/member snapshot・失効画像参照・詳細logは同じtransactionで除去する。所有装備、EXP/G/bank/STP、Trial/content clear、trophy/residence、貸出累計・券残高、初回事実には削除を伝播させない。ticket ledgerの経済記録は残す。
raw DELETEのaffected count、残存prefix、保存境界を照合してからcommitする。途中失敗はDELETEとcheckpointがまとめてrollbackし、次回は最後にcommitした境界から再開する。purgeはrollup加算を呼ばない。

### Operator手順

以下はreview後の手動運用例。本番では今回実行していない。

```sh
# まずstatus。引数なしは全profile/streamの各先頭500件をread-onlyで見る。
php artisan hakoniwa:underground:receipts:purge
# unverified_receiptなら、同じprofile/stream/cutoffで先に集計をpreview→apply。
php artisan hakoniwa:underground:receipts:aggregate --profile=123 --stream=battle
php artisan hakoniwa:underground:receipts:aggregate --profile=123 --stream=battle --apply
# 削除候補と停止理由を読み、明示的にapplyする。
php artisan hakoniwa:underground:receipts:purge --profile=123 --stream=battle
php artisan hakoniwa:underground:receipts:purge --profile=123 --stream=battle --apply
```

`--before`は30日以上前の固定cutoff、`--batch`は1〜1000。1回はprofile×streamごとに1batchだけ。`batch_limit`なら必要に応じて同じ条件で再実行する。
previewは共有profile lockによって表示を整合させるが、receipt・rollup・checkpointを書き換えない。`candidates`はそのbatchで削除可能な件数で、全backlog件数ではない。`old_receipts_in_scan`、最古時刻、停止ID/理由も返す。
将来の管理画面はこのstatusを使い、古い行があれば「古いログが溜まっています」と案内できる。管理画面自体（E）は今回実装せず、最初の削除入口は上記commandとする。

忘れ防止の定期確認には既存host cron/Compose方式の`product/docker/cron/preview-underground-receipts.sh`を用意した。環境設定`HAKONIWA_PROJECT_DIR`だけを受け、追加引数を転送せず、常にread-only previewを出力する。既存cronの運用先へこのwrapperの定期実行と出力確認を登録できる。今回cron登録・本番実行はしていない。自動DELETEの定時化は、手動運用の確認後に別途Owner判断とする。

`underground:statistics --from/--to`等は残存rawについての任意期間レポートで、出力にも`receipt_scope=retained_receipts`を明記する。30日超の削除済み期間は復元しない。生涯値は日誌のD1 totalsと`UndergroundLifetimeStatistics::totals`の保存prefix＋未集約tail、貸出はowner balanceの累計が正本。活動別・月別・日別の新しい恒久bucketは作らない。

### 検証境界

D1 schemaへ旧装備・初回事実・9件の貸出参加・既存D1 rollupをseedし、D2/D4 migration→aggregate→purgeを専用ローカルDBで通した。生成payload/出所ID、券残高/貸出累計、初回growth/tutorial/Trial文章、生涯統計が残ることを確認した。focused testではrollback/restart、pin・準備待ちの停止、previewの無変更、既存asset/progressとexpired retryを横断確認する。
恒久testを全receipt×全failureのmatrixにはしない。Fullは最終実装HEADのGitHub Qualityを正本とし、run ID/結果はPR本文へ記録する。
