# v27 baseline構造の修正

## 問題と変更境界

PR185のschema/manifestは、船PR183の基準SHA
`7c24078bb261bfd9a992b9ac3166a6b8e5c30016` のdump＋通常migrationで構築したfixtureを
既存DBの受入構造として使った。2026-10-02の本番read-only検査では、その構築経路と本番の
migration ancestryの差を検出し、通常deployを停止した。

本修正の開発基準はPR185 merge `91005f7c91f3fec4a64be300c1a1eba35277dd93`、4.9.1。
gameplay Rulesetはv27のまま。現在の本番DBをDDL/DMLでdumpに合わせず、fresh基準と
確認済みの既存構造を正確に扱う。既存採用は読み取り検査後にLaravelがmarkerを追加する
契約を維持する。通常deploy・本番migration・Web切替は本修正の実装許可に含まれない。

## 除く旧artifactと保持する保証

- `validate_monster_kill_record()` と `reject_monster_kill_record_mutation()` は旧PR21の
  `monster_kill_records` table用関数。同migrationのPR21修正で現行の
  `nation_monster_kill_stats` 方式へ置換された。現行codeとdumpに旧table/呼び出しtriggerはなく、
  2関数だけがdumpに残っていた。新freshに作成しない。既存本番にも存在しない。
- 現行のkill-stat validation/delete guard、他のpublic functions、PK/FK、資産・進行・履歴を
  保持する。古いRulesetの実行経路や旧functionのqueued-only分岐を復活させない。
- `nation_command_queue_items_world_ruleset_match` は本番と同じ
  `UPDATE OF nation_command_queue_id, command_definition_id, status` をfreshにも保持する。
  statusだけを更新した場合も現在Worldとcommand-definitionのRuleset identityを検査する。
  function body、DEFERRABLE/INITIALLY IMMEDIATEと他の制約は変えない。

## 構築経路の表記・列順差

14 tablesの20 CHECKは、固定varcharリテラル配列をtextへcastする位置だけが異なった。
値・順序・NULL条件・ANY/ALL・残りのBoolean式と、制約属性は同一である。
この限定表記を除いてSQL全体が一致することをofflineで確認した。

例：各要素の `('value'::varchar)::text` と、varchar配列全体の `::text[]`。
SQLの部分一致・任意の正規化・実DBからの自動学習は実装しない。

nationsはstate_reason/state_started_turn/resume_at_turnの物理位置だけが異なり、全列の名前・型・
NULL・default・identity/generated・collationは一致する。既存tableの再作成や列の移動は行わない。

`4_9_0_structure.json` は確認した構築経路ごとの**完全な構造hash集合**を保持する。
直接観測した本番、修正fresh、schema-only復元の3集合を保持する。復元後の集合は修正freshと
`nations`の物理列順だけが異なり、その列順は本番と一致することを完全な定義比較で確認した。
PGのdump再解析でCHECK等の表記が変わるため、復元fixtureを直接観測した本番集合と混同しない。
各集合は84 tables、79 sequencesと現行13 functionsを対象にし、いずれか一集合への完全一致を
要求する。未知の列/型/制約/索引/trigger/function差分を無視しない。
検査の比較範囲はRLS flags、列属性、制約validation/deferrability、索引valid/ready、trigger enabledを
含む。ACL/owner、view、public以外のschema、sequence現在値、業務データは構造hashの範囲外で、
それらを基準化・変更する処理も持たない。

## freshと既存採用

freshは現行schemaをロードし、既存の1 migration
`2026_10_02_000000_install_4_9_0_baseline` がcurrent catalog/v27/初期seedを作る。
新migrationを追加してfreshを2回にしない。World/Userを自動作成しない。

既存DBは受入構造に加え、必要な旧migration名、current global catalog、immutable v27 payload/
definitions、共有Worldのpublished ID参照を確認する。成功後の通常migrationでは旧ledgerを残し、
markerだけを追加する。published IDs/FKs、historical snapshot、queue、run記録、資産・進行、
sequence現在値を再解釈・再採番・変換しない。

このcheckはbaseline採用前の構造gateであり、将来の追加migrationの構造を検査するauthorityではない。
Laravelは適用済markerを再実行せず、freshでもbaseline markerの後に追加migrationを実行できる。
追加table等を適用した後に本checkを使えば、未知の構造として停止する。将来releaseでは適用前に
採用gateを実行し、適用後は当該releaseのmigration statusと個別保証を確認する。
追加migrationをこの修正へ混ぜたり、そのために現在の全体構造検査を緩めたりしない。

未知の構造、欠落ledger、catalog/snapshot/World参照の不一致では停止する。
reset/fresh/drop、ledgerの偽造・削除、CASCADE、World/queueの再束縛、turn retryで合わせない。
既存178-object dump起点環境の受入範囲は、Ownerへの確認結果を反映して確定する。

## MCPとの境界

実DBの `hakoniwa_diagnostic` 内の12 view・12 fetch関数はMCP所有であり、World dumpへ
混入していない。診断viewは14のWorld relationsへ依存するが、今回の既存採用はそのtable/columnや
診断schema/ACLを変更しない。MCP所有DDL・sourceは本PRで変更しない。

MCPのfresh-only public function preflightも旧2関数をexpected一覧に含んでいた。
MCP担当がその2項目を外し、public関数数を15→13へ変更し、残るsignature/owner/security属性と
固定12診断組の契約を維持する。修正fresh World→MCP install/exporter/profile受入を合成環境で
照合する。既存本番でMCP install.sqlをreplayすることを意味しない。

## 検証と限界

初期診断は、hash不一致15 tablesをdumpから再構成し、15/15で旧upgraded manifestのhashと
完全一致させてから本番定義と比較した。残る69 tables・79 sequences・13 functionsはhash一致。
実差はqueue triggerのstatus発火対象だけで、他は20 CHECKの限定表記とnationsの列順である。

局所検証は専用PG18.4/隔離network/資源上限を使い、fresh一回migration、固定既存schema＋
合成データの採用、status-only guard、ledger/data/sequence/依存view保持を確認する。
新SHAに対する本番baseline検査は接続のread-onlyを実測してから実行し、migrationは行わない。
確認済みの局所結果は次のとおり。

- fresh通常migration: schema load＋marker1件、current catalog/v27、World/User0、旧2関数なし。
- fresh初期化、queue正常操作、status-only guard、immutable request provenanceの5 cases:
  84 assertions、9.278秒、PHPUnitの確保memory 79 MiB。共有PCの局所値で速度評価には使わない。
- 固定既存schema＋基準7c24078から生成した合成データ: logical全行とsequenceのhashが
  `4957b722d34e59e1093f6d0f43dca97744e8ccab29984388cad03b5831ce3b06` で採用前後一致。
  旧ledger96行を保持してmarker1行だけ追加、published ID9件、v27とv26の完了run、public構造、
  QA依存viewの定義/owner/ACLを保持。再実行は変更なし。
- 既存fixtureのschema sourceは本番public schema-only（業務行なし）、SHA256
  `35cfa73f68365289eaa51aa9ba64236bb5d541b26cc4036951bd37880bc0c7dc`。
  合成行のcopy stagingではtriggerを一時無効化/再有効化し、sourceとの全行/sequence一致と
  enabledを含む構造一致を確認した。これはfixture準備だけで、既存採用の手順ではない。

初期fixture準備は既設publicとの衝突と、data-only restoreの空search_pathによるtrigger参照で停止した。
失敗fixtureを残し、新しい専用DBへ上記の検証済stagingで構築した。採用前に不一致を無視しない。
CI・review・固定SHAとMCP受入の結果はPR本文と検証記録へ記載する。

本番の全ユーザー行のhashや災害復旧リハーサルを、この局所検証の成功から推定しない。
実際の本番marker適用、deploy、mergeはOwnerの別判断として残る。
