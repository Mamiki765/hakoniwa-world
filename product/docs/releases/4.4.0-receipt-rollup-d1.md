基点：`release/4.4.0` / `62b2bc4075560f27ae30c89659524954d7ba3d09`（#158のB、#159のC1は取り込み済み）。C2はOwner判断で保留。時刻とTurn番号の追い付き／遅延補正は今回決めず、C1の上限後のcron拒否を変えない。

## 今回作ったもの

| 場所 | 内容 |
|---|---|
| `underground_receipt_rollups` | profile × streamに最大一行。恒久集計と検証済みID、直近batch情報を保持 |
| `UndergroundReceiptRollupService` | 小さい確定prefixの集約、保存後照合、checkpointの同時確定。一度集計した範囲は再加算しない |
| `UndergroundJournalService` | 集約済みの値＋未集約の原本を一つのSQL snapshotで読む。APIの名前・意味・villa条件・トロフィーは維持 |
| `hakoniwa:underground:receipts:aggregate` | 既定preview、`--apply`で集計を保存するoperator command。一回につき各profile/streamを最大一batchだけ処理 |
| migration | 新規tableとprofile/IDのseek indexだけ。旧receiptやprofileの値を変更・削除しない |

streamは`battle`、`skip`、`bulk_skip`。異なるtableのIDを一つの最大値へ混ぜない。`verified_through_id`が集約と照合の両方を終えたH/Vを兼ねる。原本を消していないので`deleted_through_id`はまだ設けない。

## 集計の意味を維持する

- 日誌の戦闘対象は探索・試練・力試しと`first_descent_tutorial`。命名story／女王決闘は境界の通過対象にはなるが、日誌の戦闘・damageへは加算しない。
- 旧soloの合計は本人の値。旧PTの合計をleaderへ帰属させない。`statistics.self`の不明値を0へ捏造しない。
- 保存はknown sumとknown countを分ける。日誌は戦闘0件なら0、全件不明ならnull、一部だけ既知なら既知の合計＋不明件数を返す。実0damageと不明を区別する。
- skip使用数は単発と一括の実`ticket_cost`の合計。skipを通常戦闘数へ加算しない。
- EXP/G/STP、銀行残高、装備、試練・女王progressへ報酬を再付与しない。案内人パンチ数も既存恒久tableのまま。
- 最大一撃、詳細な技別統計、貸出累計、回想等の将来の恒久化を「日誌の列ができたから完了」と扱わない。それらを含む原本は全部残っている。

## 安全なprefixと保存

`profile lock → 既存checkpoint → ID昇順の最大batch件 → 確定／cutoff／旧統計準備済みを確認 → 集計 → 保存と原本を読み返して照合 → commit`。

最初の未確定、保持期限内、未分類の活動、旧statistics準備待ちに当たったらそこで止める。その後ろに古い行があっても、候補から抜き出して飛び越えない。欠番はrollback由来として許容するが、別profileのIDを自分の境界へ使わない。保存／境界更新／照合は同じtransactionなので、途中で失敗すればすべてrollbackする。

旧`UndergroundBattleHistoryCompactor`は未準備行のstatisticsを書き換え得るため、battleは既存compaction versionへ準備済みの行だけ集約する。これは不明値のあるPTを永久保存する条件ではない。準備後にself値が不明でも、unknownとして正常に集約できる。旧4.2.1の固定cutoff作業を今回再実行しない。未準備が報告された場合のみ、その具体的な残件を先に調べる。

[Runtime](../../app/Application/Underground/UndergroundRuntimeService.php)、[Intro](../../app/Application/Underground/UndergroundIntroService.php)、[Playtest](../../app/Application/Underground/UndergroundPlaytestService.php)の既存writerはprofileを直列化してからreceiptを作る。ID境界はこの書込順とPostgreSQLの昇順／非cycle／CACHE 1 sequenceが前提。commandはsequenceをread-onlyで確認し、満たさなければ停止する。低いIDを手動挿入する補修や、集約済み統計の後日再計算は別途、集計への差分反映も含めて扱う。

日誌では、集計行を読んだ後に別queryで境界を読まない。集計済みの原本がまだ残っていても、`id > verified_through_id`だけを足す。三streamともUNION ALLから集計する一つのstatementなので、collectorのcommitを跨いだ二重計上／欠落を避ける。

## command（説明例。今回、本番実行していない）

```console
php artisan hakoniwa:underground:receipts:aggregate --profile=1 --batch=500
php artisan hakoniwa:underground:receipts:aggregate --profile=1 --before="固定cutoffのISO日時" --batch=500 --apply
```

`--before`省略時は、その起動の30日前で固定する。30日以内の時刻は拒否する。`--profile`省略時は既存profileを巡回するが、各streamは一回に最大一batch（上限1000件）。`batch_limit`なら次の明示実行で続きから処理する。`--stream=battle|skip|bulk_skip`で限定可能。

previewはcheckpointすら新設せず、候補境界とdeltaを表示する。applyは検証成功したprefixだけを確定する。準備待ち等の停止があればJSON結果で理由を示して非ゼロ終了し、それまで成功した別の小batchは報告どおり残す。全対象を一つの長いtransactionにしない。**いずれも原本は削除せず、HTTP endpoint／scheduler／cron登録は追加しない。**

## まだ必要なDの後続

| 残件 | 原本を削る前に必要なこと |
|---|---|
| 所持装備の出所 | 短命receiptへのCASCADEとinstance CHECKを一緒に整理。所持品を巻き込まない |
| 貸出報酬 | 原本COUNTから恒久参加数／繰越へ移行。10回境界・日次上限・再送を維持 |
| 回想・初回の事実 | 既存の試練／女王恒久記録を再利用し、receipt依存の初挑戦文等を保存 |
| 統計の残す範囲 | 日誌以外の必要な事実を小さい恒久集計へ。全receiptコピーや無限UUID台帳は作らない |
| 期限後request | 消した古いUUIDが新規決算として再実行されない受付移行。仕様未決を勝手に有効化しない |
| 検証済み原本の削除 | 上記を整えた後だけH/V内の期限超過確定prefixを削除。削除済み境界と中断再開を追加 |

現在のD1をdeployできたとしても、既存raw tableへ単純な30日DELETEを行ってよい意味ではない。

## このbranchに同梱したrelease同期

Owner指定により[Forgejo同期](../../../docs/operations/github-to-forgejo-mirror.md)へ`release/*`を追加。小branchは`codex/*`等を使用し、release親と分離する。新しいrelease branchだけ初回作成を許可し、既存branchはfast-forwardのみ。認証失敗を「branchがない」と解釈しない。削除伝播／force push／deployはしない。

この変更がreleaseへmergeされるまで、releaseの自動同期はまだ旧設定のまま。D作業branchだけにある変更や、別のcontent-blueprints branchも自動保管済みとは扱わない。
