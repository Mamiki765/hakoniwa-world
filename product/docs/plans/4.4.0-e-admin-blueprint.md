# E：管理ページ・配布・島整理 blueprint（仮）

2026-09-22／調査基点 `8060bb0572d2de737c4b9516e3b2c9c22b55e835`。Owner精査用。画面と接続先を組むための設計で、管理API・配布・削除を実装／実行した記録ではない。C1とは別branchで扱う。

## 1. Owner指定と画面の骨格

お問い合わせ一覧は現在の場所に残す。それ以外は「管理」へ案内し、管理ページは各機能へのボタン・案内リンクにする。最初の実機能は配布と島整理。島整理は違反者処分だけでなく、長期不在や短期離脱島を整理して海のスペースを空ける用途を含む。

```text
管理 [配布] [島管理] [お知らせ] [案内人の会話] [運用案内]
       └ 対象 → 内容・理由 → 確認 → 登録結果
              島管理 └ 対象島 → 処理範囲・理由 → 確認 → 結果
```

推奨UI名は「島管理／島の整理」。内部の処分理由で違反を選べるが、全対象へ制裁・BANの表示を付けない。別ページか折畳みかは既存Appの構造に合わせる。最初から汎用ダッシュボード、権限編集、管理者の追加、全履歴検索を作らない。

## 2. 既存コードへつなぐ位置

| 確認・既存の入口 | 利用方法の案 |
|---|---|
| `product/routes/web.php` の `/api/v1/admin` | 現在も問い合わせ・お知らせ・会話編集をここへ集約。新しい管理操作も同じ認可・private response境界へ置く |
| `RequireAnnouncementAdmin` → `AnnouncementAdminAuthorizer` | 既存の管理者判定をAPIでも再利用。UI非表示だけにしない。名称変更のためだけに権限体系を作り直さない |
| `CompensationWarehouseService::createGrant` | 配布倉庫を作り、既存の受取経路へつなぐ。管理画面から残高を直接加算する別ルートを作らない |
| `NationAbandonmentService` / `NationAbandonmentOperation` | cleanup処理を共有し、管理者の実行source・理由を加える。本人へなりすましてmanual abandonを呼ばない |
| `AnnouncementController`、既存public event | 告知の正本を再利用。削除結果と食い違う第二のニュースDBを新設しない |

管理権限を変更する提案ではない。問い合わせ一覧を移動・削除する提案でもない。

## 3. 配布の最小縦切り

最初は一つの島を選ぶ → 現在ownerと配布内容を確認 → 倉庫へ登録、まで。既存serviceが扱う資金・食料・石油・Pd・skip券・地下Gから必要なものを出す。紋章など任意アイテム配布は別途catalogができてからでよい。

入力は対象、配布理由、正の量、同一配布のrequest ID。実行者は認証済み管理者からサーバーが取得する。確認画面では「所持残高へ直接反映」ではなく「配布倉庫に登録」と説明する。既存のgrant key再送検出を使い、二度押し・再読込で別の配布を作らない。

対象ownerが確認後に変わった場合は再確認。島整理済み・受取対象が変わった配布を別の島主へ黙って転送しない。全島配布は対象一覧と件数の確認を追加する第二段階でよく、初版にCSV取込・予約配布・配布campaign基盤は要らない。

API案（未実装の名称案）：`POST /api/v1/admin/distributions`。previewは小さい画面内表示で足りるか、サーバー側の対象確定が必要かを既存serviceと相談する。単なる文章previewのためだけに恒久テーブルを追加しない。

## 4. 島整理の最小縦切り

対象島の名前・番号・owner・状態・最後の活動情報を表示し、理由と公開文を入力する。理由の候補は「長期不在による整理」「本人希望」「運営上の整理」「規約違反」「その他」。選択肢は案であり、この分類をDB enumへ固定する必要はない。

確認では「何を海に戻すか」「現役の船・予約・資源がどうなるか」「秘書・地下資産は残る」を明示する。既存abandon処理は所有地以外に首都周辺の中立地にも影響し得るため、対象範囲を“島の名前だけ”で説明しない。

実行はWorld排他／未解決Turn guard／最新状態確認の下で、既存cleanupと監査を一つのtransactionへまとめる。`actor_user_id=管理者`、対象owner、理由、source=`administrative`（仮）を区別して残す。既存のowner一致検証を全面的に撤去せず、管理者専用入口で許可する。User、Secretary、UndergroundProfileの削除へ拡大しない。

処理と告知は同じ実行IDに紐付ける。告知に個人情報・内部通報の全文をそのまま公開しない。公開を選んだ場合の文案例：

> 運営による島整理：○○島は長期不在のため整理しました。違反処分ではありません。秘書・地下の進行は保持されます。

公開を必須にするか選択にするか、全文公開か公開用の別文面かはOwner確認点。理由の記録自体は必須という方向。

競売escrowがある場合、初版は既存決算を待つ案が最小。強制取消・返金まで必要ならその決算を同じPRで明示設計する。今の「365日」の自動整理期限を勝手に短くしない。

## 5. 保存先・完了条件

配布は既存grant/claim、島整理は既存Nationのabandoned状態と監査／告知が正本。単に画面を分けるためにadmin_jobsテーブルを作らない。管理者の将来の一括処理が必要になった時に改めて考える。

実装時の最小確認は、管理者以外が配布・島整理できないこと、同じ操作の再送で重複しないこと、既存abandon代表で秘書・地下資産が残ること、理由と告知が対象を取り違えないこと。既存の代表を使い、全理由種別×全資産×全画面のテスト表にはしない。

完了は管理画面から実際のserviceまでつながること。ボタンがあるだけのHTML見本は実装完了としない。
