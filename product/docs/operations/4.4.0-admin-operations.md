# 4.4.0 管理ページ・配布・島整理

管理者は既存のDiscord ID認可を使用する。TOPのお問い合わせ一覧にある「管理ページへ」から配布・島整理・お知らせ・案内人の会話・ログ整理を開く。お問い合わせ一覧と、Ownerが追加指定したTurn進行操作は管理者TOPに表示する。

## 配布と倉庫

- 「全User」は島なし・休眠を含む、確認時点の全User。島番号、秘書ID、User IDは明示的に選択する。手入力は`1-4,10,14,15`形式で、一覧選択との重複はUser単位で除く。秘書一覧は直近7日以内の完了戦闘・単発/一括スキップから抽出する。
- 内容確認には解決済みUser一覧・1人あたりの資産量・公開する配布理由を表示する。実行時に「全User」を再解決しない。確認情報は管理者・World・操作・サーバー発行identityへ結び付ける。有効期限は1時間。実行済みの再送は保存結果を返す。
- 操作結果は既存auditの`admin.operation_completed`へ保存する。request identityの部分unique indexを追加し、再送結果の検索と重複防止に使う。
- 既存の配布倉庫・容量上限・Pd/券ledger・地下G加算を使う。受取Userを正本とし、`nation_id`は発行時の島の来歴として残す。旧grantも島を手放しただけでは失効しない。
- ログイン中の「配布倉庫」は島なしでも開ける。Pd・スキップチケットはUserへ、地下Gは既存の地下profileへ加算する。地下profileがまだなければGは保留する。地上資産は受取時点でそのWorldに所有する島へ加算し、島なしや容量不足分は倉庫に残す。
- 発行から365日後を`expires_at`とする。既存grantはforward migration実行時から365日後に設定する。既存の配布量・受取量・claim結果は変更しない。
- 「あとN日」は残り時間の日数切上げ。期限到達以後は受取不可。期限切れ判定は受取処理にもあり、一覧取得または期限切れgrantへの受取要求で`expired`を保存する。未受取量を受取済みに書換えず、grant・items・claim履歴を保持する。履歴画面は直近100件を表示する。
- 応答喪失時は「結果を確認する」「受取結果を再確認する」で同じ操作を再送する。表示再取得の失敗から自動的に再配布・再受取はしない。

## 島整理

対象島・公開理由・競売の状態を確認して明示実行する。公開理由は重大ニュースへ載せ、運営備考はadmin auditだけへ残す。実行管理者と対象ownerを区別する。

既存のmembership lock → World lock → transactionを使い、未解決Turn中は整理しない。対象が出品者または最高入札者である競売だけを既存決算へ流す。入札があれば最高入札で決算し、なければ返却して終了する。自動再出品やNPC生成は行わない。別の島が受け取る資金・商品も既存の上限・手数料・所有権移転を使う。

その後、既存の島破棄処理を呼ぶ。User・秘書・地下進行は残し、島の地上資産・船・領域・予約等を同じ範囲で整理する。対象が落札した商品も既存どおり受け取り、地上資産はその後の島破棄対象、秘書ItemはUser側へ残る。決算・島整理・公開ニュース・実行結果auditは一つのtransactionで確定し、再送で重複させない。

## 古いログ

管理ページ上部の「古いログが溜まっています」はD4のread-only previewを使用する。profile × streamの先頭500件にある古い記録・削除候補・最古時刻・停止理由を示す。全履歴の総件数ではない。

各区分を確認後、明示実行した場合だけ同じD4 purge serviceへ渡す。候補範囲が変わった場合は確認をやり直す。恒久集計・検証・pin・active story・連続prefixの条件はD4から変えない。集約不足なら先に既存のaggregate commandで準備する。schedulerは引き続きread-only previewのみで、自動DELETEは追加しない。

## Worldの予定起点と手動Turn

`worlds.turn_schedule_origin_at`はそのWorldのTurn 1の予定時刻。新設Worldでは作成時点のJST偶数時を保存する。次回Turn予定は既存`TurnScheduleStatus`で、起点 + `current_turn × interval_hours`として求める。遅れて実行した完了時刻に予定を合わせ直さないため、2ターン遅れを1ターンだけ回復しても残りの遅れを維持する。

既存Worldの起点は、migrationが履歴から推測して埋めない。未設定の間は旧方式で状態表示を継続し、Web手動進行は利用不可とする。実際のWorld開始記録を確認して、deploy時の独立した承認の下で一度だけ初期設定する。

Ownerが本Worldについて確認したTurn 1は2026年8月6日00:00 JST。これはこのWorldの運用値であり、runtimeの固定日付・他Worldのdefaultではない。

```sh
# previewのみ。本番では今回未実行。
php artisan hakoniwa:turn:schedule-init --world=shared-world --origin=2026-08-06T00:00:00+09:00
# 内容を確認し、本番操作の承認後にのみ実行する。
php artisan hakoniwa:turn:schedule-init --world=shared-world --origin=2026-08-06T00:00:00+09:00 --apply
```

このcommandはTurnを実行せず、設定済み起点の上書きも行わない。

Webの「Turn進行を試みる」は、World lock取得後、既存`next_scheduled_turn_at`を現在時刻が過ぎたことを再確認する。表示時の次targetに固定し、既に完了したtargetへの再送は完了結果を返す。新しい強制処理はなく、既存`TurnRunner`の`source=manual`を呼ぶ。同じtarget/ruleset/seedとfailed/blockedのmanual retry条件、C1のDB session保護を保持する。実行後は状態を再取得する。CLI/cronの契約・自動retryは変更しない。
