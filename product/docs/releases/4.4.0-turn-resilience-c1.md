# 4.4.0 C1：同一起動内の限定Turn retry

実装基点：`8060bb0572d2de737c4b9516e3b2c9c22b55e835`（#158取り込み後）。Ownerが2026-09-22にChat側のC1実装・commitを依頼。C2、scheduler、Ruleset、schema、実際の本番操作は含めない。

## D-02の採用差分

初期公開版の「自動retryなし」に対する変更は、**Turn transaction本体が投げたPostgreSQL SQLSTATE `40P01` / `40001`を、同一起動内で初回込み最大3回まで再実行する**ことだけ。`prepareRun`の後日のcron拒否、manualの同run/target/ruleset/seed、release跨ぎの拒否は維持する。

再試行するのは、外側transactionを持たない通常Turn起動で、Laravelのroot rollbackが正常終了し、同じPDO/sessionでtransactionが終了している時だけ。エラー文字列の「deadlock」は条件にしない。Laravelのnested `DeadlockException`はcause内の最初の構造化PDOエラーへ遡り、23505等を誤ってretryしない。

commit/after-commit段階の例外は、たとえ40001であってもC1では対象外。rollback完了をこの経路で保証できないためであり、任意の接続断・stale-runningも自動復旧しない。confirmed completed行は失敗記録で上書きしない。これは全てのcommit failureを自動修復する変更ではない。

## 処理順

`World advisory lock → prepareRun → RUNNING → attempt transaction → 全phase → current_turn/COMPLETEDを同時commit → lock解放`。

retry対象の失敗なら、完全rollback後に同runの`attempt_count`を増やし、次のattemptへ進む。中間の失敗を外部の新runや追加Turnとして扱わない。`started_at`は起動内の最初の開始を維持する。

既存`failure_context`に最大2件の`transient_retries`（attempt_count/phase/sqlstate）を残す。回復成功時もこの短い診断は残し、status=completedとnull failure_codeが結果の正本。終端失敗は最後のphase・exception_class・sqlstate・起動内試行数を持つ。後日のmanual retry開始時は従来通りfailure_contextをクリアする。

## PHP側の状態の点検

| 保持しているもの | 各試行での扱い |
|---|---|
| World model / TurnContext / TurnState / RNG / phase_results | locked Worldを取り直し、context/state/RNG/結果配列を新規作成。再試行前のrun modelはrefresh |
| MonsterRemovalService（singleton） | **全phaseより前にresetForAttempt**。batch、run/world/attempt識別、complete判定、removedCountをクリア。rollbackしたEloquent snapshotを持ち越さない |
| MissileImpactResolver | 既存process_cellsの`begin()`がlaunches、changed cells、地下基地処理済み集合、cell/ship参照を初期化。新しいgeneric reset機構は追加しない |
| SurfaceShipTurnService | 既存`load()`でその試行のship batchと定義/資源/移動設定を構築 |
| MonsterTurnService | `load()`で占有batchを再構築し共有removalへ設定。保持するsea/wastelandはread-only定義 |
| CompleteTurnEngineのdefinition caches | 同じ固定Rulesetのread-only resource/facility/terrain定義。player残高・map cell等の可変状態として再利用しない |
| TurnEventRecorder / DomesticCommandExecutor / DisasterTurnService | 決算値・イベントは各呼出しのlocal/context/DB上。失敗transactionのイベントを再利用・再加算しない |

この確認は上記のコード経路を読んだもの。全serviceを反射で捨てる、pipeline自体を勝手に新しい設定から再解決する、別catalogへ逃がす、といった仕組みは追加しない。同seedでも、失敗の間に許可された別操作が確定した場合までDB入力が同一であるとは主張しない。

## 検証の焦点

既存TurnRunnerTestのmanual rollback/retry、cron failed/blocked拒否、canonical pipeline・排他代表を維持する。追加はC1の独立した意味3件だけ。

1. PostgreSQLのnested 40P01→40001→成功。実際のDB rollback、同run/seedとRNG再構成、singleton怪獣状態のリセット、1回だけのWorld更新・怪獣除去イベントを確認。
2. 最大3回で停止、次回cronは依然拒否、manual回復で同run/seedを再利用。
3. メッセージにdeadlock/40P01が含まれても、構造化SQLSTATEが23505なら1回で停止。

追加testは`DatabaseMigrations`と既存forward-only helperを使い、外側のtest transactionではなく実root transactionを対象にする。SQLSTATEは決定論的なDB fault injectionであり、実際に二接続の待機循環を発生させるテストとは区別する。sleep、固定query本数、全phase×全エラーのmatrixは追加しない。

実行証拠はPR/CIの固定HEADで確認する。この文書自体はCI成功・本番適用の証拠ではない。Chatのlocal環境ではPHP構文確認とSQLSTATE判定の小さいprobeを実行し、Laravel/PDO PostgreSQLによる実行はCIへ委譲する。

## 運用

手動の利用方法・cron登録は変わらない。3回失敗後のOwner待ちは残る。次工程C2はこのPRに混ぜず、失敗種別・実行互換性・再開条件・通知を別途決める。#158の旧web停止を伴うschema切替条件も変えない。
